# CS-359 — Post-OCR Celery pipeline (F2 → rubric → delivery handoff)

## Context

Public `POST /api/v1/submissions/` completed OCR and left submissions in `processing_status=extracted` with **no** server-side continuation into `F2Orchestrator`, rubric finalization, or delivery — so polling clients never observed `completed` with nested analysis. Extracted text must not be persisted in Postgres ([[CS-057]]); a **short-TTL Redis envelope** hands off `{extracted_text, delivery_channel, delivery_target}` to a Celery worker that atomically claims work (`extracted` → `classifying`) before enqueue.

## Scope

**In:**

- Redis stash + load/delete semantics safe under Celery retries (`backend/ingestion/infrastructure/redis_handoff.py`).
- `schedule_post_ocr_pipeline` after successful OCR: store handoff → atomic claim → `transaction.on_commit` → `ingestion.process_submission_pipeline` (`backend/ingestion/application/post_ocr_pipeline.py`).
- Worker task: F2 → attach `ContractSubmission.analysis_id` → `analyzing` → synchronous rubric evaluation → delivery enqueue / web-link availability → `completed` (`backend/ingestion/infrastructure/celery/pipeline_tasks.py`).
- Multipart `delivery_channel` / `delivery_target` parsed on upload without persisting raw targets pre-analysis.
- Idempotent re-upload still progresses pipeline when `analysis_id` is null and status remains `extracted`.
- Integration tests + Railway worker documentation (`RAILWAY.md`, `.env.example`).
- FE: on poll timeout, optional readiness probe + softer delivery-expectation copy (`frontend/src/server/contract-env.ts`, `frontend/src/server/contract-backend.ts`).

**Out:**

- Replacing internal `POST /api/v1/internal/classify` QA surface.
- Product SMS/email provider verification beyond enqueue wiring.

## Acceptance criteria

- [x] Given OCR lands on `extracted` with handoff stored, when claim succeeds, then Celery task runs F2, persists `ContractAnalysis`, sets submission `analysis_id`, runs rubric so `score_total` is populated, sets `processing_status=completed`, and applies delivery channel intent without logging raw text or targets.
- [x] Given concurrent duplicate schedules, when two workers race the claim `UPDATE … WHERE processing_status='extracted'`, then exactly one enqueues; the loser does not delete another winner’s Redis payload.
- [x] Given Celery retry after partial progress, when Redis handoff uses load semantics until explicit delete, then text remains available until terminal cleanup.
- [x] Given `CELERY_TASK_ALWAYS_EAGER` or direct task invocation in tests, when mocked F2/rubric/delivery boundaries, then GET submission shows terminal `completed` and nested analysis identifiers as expected by [[CS-296]] polling.
- [x] Given deployment without a Celery worker, when operators follow `RAILWAY.md`, then they see explicit verification steps (worker service + shared broker/Redis + `pipeline.task.*` logs).

## Implementation pointers

- Handoff + settings: `INGEST_HANDOFF_REDIS_URL`, `INGEST_HANDOFF_TTL_SECONDS`.
- Task name: `ingestion.process_submission_pipeline`.
- Delivery bridge: `backend/delivery/application/post_analysis_delivery.py` (web link path aligns with existing DTO/tests).

## Notes

- Ops must run **`celery -A config worker`** (or project-documented equivalent) with **same** broker/DB/env as web — queues otherwise never drain.

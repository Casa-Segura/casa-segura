# CS-248 — Resend endpoint with hash verification + three-resend cap

## Context

Humans lose email/message access; guarded resend restores delivery **only** to original destination hashed on file ([[RUBRICA_CONTRATO]] §13.4, [[PRD_F7_ENTREGA_MULTICANAL]] §3 US-05).

## Scope

**In:**
- `POST /v1/contracts/{public_short_id}/resend` body `{ "target": "...email or E.164 phone..." }` per §7 schema
- Hash compare user supplied target vs persisted `delivery_target_hash` / analysis-level mirror per §5
- Respect **maximum 3 resends** cumulative after initial successful delivery per BR-05 (define whether initial send counts — PRD: *"counting all requests after the original delivery"* → increment `resend_count` only after first success)
- Enforce **channel stickiness** BR-12 (SMS resend cannot switch to email)
- Queue new `DeliveryRequest` with `is_resend=true` linked parent id
- Response `202` JSON per §7 example with channel echo

**Out (explicit):**
- Destination change requests (always forbidden)
- Link-only resend (BR-13 says link access itself resend — no hash) — do not require this endpoint for web-link users

## Acceptance criteria

- [ ] Given mismatching target, returns `403` JSON error code `TARGET_MISMATCH` copy Spanish per §7
- [ ] Given `resend_count ≥ 3` additional attempts return `429` `RESEND_LIMIT_EXCEEDED`
- [ ] Given expired link (`link_expires_at <= NOW()`), returns `410 Gone` with domain-specific error `LINK_EXPIRED` and does not enqueue send
- [ ] Successful enqueue increments `resend_count` atomically under row lock
- [ ] Logs exclude raw `target` at INFO; only metadata

### BVA — boundary value analysis

| `resend_count` | Boundary | Expected |
|---|---|---|
| 2 → 3 | third allowed | 202 Accepted |
| 3 → 4 | fourth blocked | 429 |
| Hash compare | off-by-one char | 403 |

## Test intent (Rule 9)

Permitting resend after hash mismatch enables phishing-forward of reports — negative tests must cover case-insensitive email normalization rules explicitly encoded.

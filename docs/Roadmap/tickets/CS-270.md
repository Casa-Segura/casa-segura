# CS-270 — Choose retention job scheduler and document ADR

## Context

[[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] requires five recurring jobs (`cleanup_transient`, `cleanup_delivery_targets`, `expire_links`, `anonymize_old_analyses`, `recompute_project_metrics`) plus observability that they run on time ([[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] §6.2, BR-13). This ticket locks how those jobs are hosted (in-process scheduler vs OS cron invoking CLI) so downstream tickets implement runners against one contract.

## Scope

**In:**
- Decision between APScheduler (or equivalent) inside the worker/API process vs external cron invoking `python -m ...` entrypoints
- ADR note in-repo: trade-offs (single vs multi-instance, exactly-once vs at-least-once, deploy platform constraints, failure visibility)
- Standard interface for all jobs: name, idempotent run, structured metrics (start/end, rows affected, errors), exit codes for cron
- Timezone default [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] §6.3: `America/El_Salvador` for `anonymize_old_analyses` daily at 03:00 local (UTC-6)

**Out (explicit):**
- Implementing individual job SQL/business logic — [[CS-271]], [[CS-272]], [[CS-273]], [[CS-274]], [[CS-275]]
- Internal HTTP trigger auth — optional follow-on if ADR chooses API-trigger only for ops

## Acceptance criteria

- [x] Written ADR lists chosen approach, rejected alternatives, and how duplicate schedulers are prevented in production (or explicitly accepts at-least-once + idempotent jobs)
- [x] Documented schedule table matches [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] §6.2: `cleanup_transient` ≤15 min; `cleanup_delivery_targets` ≤5 min; `expire_links` ≤1 h; `anonymize_old_analyses` daily 03:00 America/El_Salvador; `recompute_project_metrics` ≤1 h
- [x] Each job has a single documented entrypoint (module path or callable) that operators can run manually
- [x] Metrics emission contract defined (minimum: job name, `started_at`, `completed_at`, `status`, `records_processed`) aligned with [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] BR-13
- [x] CI or local `make`/script runs a dry-start of the scheduler harness without connecting to production DB

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| `cleanup_transient` cadence | 15 min nominal | Config supports ≤15 min; alert if no success in ≥2× interval |
| `cleanup_delivery_targets` cadence | 5 min nominal | Config supports ≤5 min; alert if no success in ≥2× interval |
| `expire_links` cadence | 60 min nominal | Config supports ≤60 min; alert if no success in ≥2× interval |
| `recompute_project_metrics` cadence | 60 min nominal | Config supports ≤60 min; alert if no success in ≥2× interval |
| Daily anonymization | 03:00 America/El_Salvador | Job fires once per local calendar day (DST rules documented if any) |

## Test intent (Rule 9)

Alerts and on-call response depend on **wall-clock expectations** tied to El Salvador local time and sub-hour cleanup SLAs. Tests must fail if the ADR’s schedule table drifts from [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] §6.2 or if dual schedulers could run the same job unsafely without documentation.

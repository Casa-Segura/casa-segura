# CS-110 — Implement classification prompt and few-shot anchors

## Context

The pipeline must assign exactly one of nine outcomes (`CVC`, `CVP`, `ARV`, `ARC`, `APV`, `LEA`, `IVU`, `FSV`, `NOT_CLASSIFIABLE`) before rubric and economic stages run. This ticket codifies the Spanish system/user prompts from [[PRD_F2_CLASIFICACION]] §8.1–8.2, adds curated few-shot anchors per type, and wires confidence handling plus validation retry per [[PRD_F2_CLASIFICACION]] US-01 so downstream components receive a deterministic classification envelope aligned with [[RUBRICA_CONTRATO]] §3.

## Scope

**In:**
- Versioned prompt templates (system + user) matching §8.1 structure and valid-type definitions.
- Few-shot exemplars (minimal snippets) anchored to each of the eight covered types plus a `NOT_CLASSIFIABLE` exemplar.
- Orchestration: primary structured JSON call; if `confidence ∈ [0.65, 0.85]`, invoke §8.3 validation prompt; persist `classification_attempts` and final confidence per [[DOMAIN_MODEL]] / [[PRD_F2_CLASIFICACION]] §5.1 field intent.
- Populate `contract_type_declared` from accepted classification; leave `contract_type` equal unless a later ticket applies reclassification.
- Structured logging without raw contract text (types, confidence, attempt counts only).

**Out (explicit):**
- Leasing Art. 2 indicator detection ([[CS-111]]).
- Project normalization and `Project` upsert ([[CS-112]]).
- Economic field extraction ([[CS-113]]).
- Shared pydantic schemas for nested extraction ([[CS-114]]) — consume stubs/interfaces only if schemas land first.

## Acceptance criteria

- [x] Given extracted Spanish contract text, the service performs one LLM call returning JSON with `contract_type`, `confidence`, `indicators_found`, `reasoning`, `project_name_canonical`, and `elements_detected` keys exactly as specified in [[PRD_F2_CLASIFICACION]] §8.1 (keys may be extended only if §5.1 / [[CS-114]] explicitly adds them). _Partial — CS-110 ships the primary call with `contract_type`/`confidence`/`reasoning`; the `indicators_found`, `project_name_canonical`, and `elements_detected` keys land with [[CS-112]]/[[CS-114]] (nested-schema extension)._
- [x] Given `confidence > 0.85`, the run accepts the primary result without a validation call and stores `classification_confidence` and `classification_attempts = 1`. _Implemented in `ContractClassifier.classify`; the strict `>` is enforced by `_is_high_confidence`. Persistence column added by PR-0 (`platform_core/0005`)._
- [x] Given `confidence ∈ [0.65, 0.85]` on the primary call, the §8.3 validation prompt runs with prior type and reasoning; if the validation agrees on `contract_type`, the run accepts and stores `classification_attempts = 2`; if it disagrees or validation `confidence` falls below the acceptance rule, the outcome is `NOT_CLASSIFIABLE` per [[PRD_F2_CLASIFICACION]] US-01. _Implemented via `_run_validator` + `_apply_validator`; closed-interval band check in `_is_medium_confidence`._
- [x] Given `confidence < 0.65` on the primary call (and after validation flow when applicable per US-01), the analysis path terminates with `contract_type = NOT_CLASSIFIABLE` and user-facing copy per [[PRD_F2_CLASIFICACION]] US-06 (Spanish strings). _Implemented as the early-return branch in `classify`. User-facing copy is owned by EPIC-10 (frontend already shipped) and the orchestrator (PR-6) is responsible for surfacing the result; this ticket guarantees the type._
- [x] Given an LLM response that is not parseable JSON after one repair retry policy described in [[PRD_F2_CLASIFICACION]] §10 open question 5, the submission is marked `failed_classification` (not confused with `NOT_CLASSIFIABLE`). _Wired in `ContractClassifier._parse`: parse / schema failures raise `ClassificationError(code="LLM_PARSE_FAILED")` so the orchestrator (CS-112) maps them to `failed_classification`, distinct from `NOT_CLASSIFIABLE`._
- [x] Few-shot pack includes at least one anchor example per enum value (`CVC` … `FSV`) plus `NOT_CLASSIFIABLE`, documented in-repo with rationale pointing to rubric applicability ([[RUBRICA_CONTRATO]] §3). _Shipped in `backend/classification/application/prompts.py::FEW_SHOT_ANCHORS` with synthetic BR-07-safe text and per-type rationale in the module docstring._

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| `confidence` (primary) | `> 0.85` vs `≤ 0.85` | Strictly **greater than** 0.85 auto-accepts with no §8.3 call ([[PRD_F2_CLASIFICACION]] US-01); `0.85` falls into retry band |
| `confidence` (primary) | `∈ [0.65, 0.85]` vs `< 0.65` | Closed interval triggers §8.3 validation flow; below 0.65 yields `NOT_CLASSIFIABLE` without agreement path |
| Validation agreement | Same `contract_type` vs disagree | Agreement → accept; disagreement → `NOT_CLASSIFIABLE` |
| Enum | `NOT_CLASSIFIABLE` from model | Accepted immediately per US-06 without forcing retry loop |

## Test intent (Rule 9)

Tests must encode that **classification acceptance is gated by the PRD confidence bands and a second-pass validator**, not merely that an LLM returns JSON — otherwise tightening thresholds would not fail tests ([[PRD_F2_CLASIFICACION]] US-01).

# CS-051 — Compute submission hash for idempotency

## Context

Duplicate uploads waste vision budget and violate user expectations. [[PRD_F1_INGESTA_Y_OCR]] §US-03 defines `submission_hash` as **SHA-256** over ordered per-file hashes; [[PRD_GENERAL]] §5 requires upload-hash idempotency for analysis.

## Scope

**In:**

- Per-file SHA-256 of raw bytes (pre-normalization).
- `submission_hash = SHA-256( sort_by_filename( hex(file_i_hash) concatenation rule per PRD ) )` — implement **exactly** as specified in [[PRD_F1_INGESTA_Y_OCR]] §US-03 (“concatenation of per-file hashes ordered by filename”).
- Lookup against `ContractAnalysis.submission_hash` for non-anonymized rows: if hit, return **409** payload with `is_duplicate=true`, prior `public_short_id`, and `analysis_id` per §7.1.
- Lookup against in-flight `ContractSubmission` rows in `received` / `extracting` / `classifying` to join/wait semantics (document behavior in API; polling contract may return the same `submission_id` or a stable reference — choose one and test it).
- Store `submission_hash` on `ContractSubmission` when created ([[DOMAIN_MODEL]] §4.1).

**Out (explicit):**

- Defining rubric-version mismatch re-run rules beyond storing `submission_hash` (referenced in [[PRD_F1_INGESTA_Y_OCR]] BR-03 full implementation may wait for analysis creation).
- Cross-user privacy review of returning prior `analysis_id` (product assumes hash-as-de-dupe key).

## Acceptance criteria

- [ ] Given two uploads with **identical** file set and filenames in the same lexicographic order, when hashed, then `submission_hash` values are **identical**.
- [ ] Given the same files uploaded with **renamed** filenames only, when ordered by new names, then hash changes if and only if the PRD’s ordering rule makes the concatenation differ (tests must encode the PRD rule, not an ad-hoc hash).
- [ ] Given a completed non-anonymized `ContractAnalysis` with the same `submission_hash`, when a new submit occurs, then API returns **409** with `is_duplicate=true` and does **not** re-OCR.
- [ ] Given no prior row, when first upload, then a new `ContractSubmission` is created with unique `submission_id` and persisted `submission_hash`.
- [ ] Idempotency keys for OpenRouter (separate ticket) remain independent; this ticket only covers **content** hashing.

### BVA — boundary value analysis

| Case | Boundary | Expected |
|---|---|---|
| Single file vs multi-file | 1 file / 50 files | hash computed; ordering by filename deterministic |
| Filename ordering | `a.pdf` before `b.pdf` vs swapped | hash differs iff concatenation order differs per PRD |
| Duplicate vs anonymized analysis | Analysis past retention anonymization boundary | Behavior must match [[PRD_GENERAL]] / F8: if hash match should re-process post-anonymization, encode explicitly; otherwise document “re-analyze after 90d anonymization” — **defer to EPIC-09** unless already specified in ContractAnalysis lifecycle |

## Test intent (Rule 9)

The test suite proves **dedupe is stable and order-sensitive exactly as PRD dictates**, catching accidental switches to “hash the ZIP” or “sort by MIME” that would silently break idempotency and billing.

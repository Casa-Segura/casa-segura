# CS-051 — Compute submission hash for idempotency

## Context

Duplicate uploads waste vision budget and violate user expectations. [[PRD_F1_INGESTA_Y_OCR]] §US-03 defines `submission_hash` as **SHA-256** over ordered per-file hashes; [[PRD_GENERAL]] §5 requires upload-hash idempotency for analysis.

## Scope

**In:**

- Per-file SHA-256 of raw bytes (pre-normalization).
- `submission_hash = SHA-256( sort_by_filename( hex(file_i_hash) concatenation rule per PRD ) )` — single-file collapses to `sha256(file_bytes)`.
- Store `submission_hash` on `ContractSubmission` when created ([[DOMAIN_MODEL]] §4.1).
- Lookup against in-flight `ContractSubmission` rows; idempotent re-upload returns the original submission with HTTP 200.

**Out (explicit):**

- Lookup against completed `ContractAnalysis` rows to return 409 `is_duplicate=true` — **blocked by [[EPIC-04]] / [[EPIC-06]]** (ContractAnalysis lifecycle + cross-row linkage). Scope deferred to that epic's first ticket.
- Defining rubric-version mismatch re-run rules beyond storing `submission_hash` (referenced in [[PRD_F1_INGESTA_Y_OCR]] BR-03 full implementation may wait for analysis creation).

## Acceptance criteria

- [x] Given two uploads with **identical** file set and filenames in the same lexicographic order, when hashed, then `submission_hash` values are **identical** (`test_multi_file_hash_is_deterministic_under_filename_ordering`).
- [x] Given the same files uploaded with **renamed** filenames only, when ordered by new names, then hash changes if and only if the PRD's ordering rule makes the concatenation differ (`test_multi_file_hash_changes_when_filename_changes`).
- [x] Given a prior `ContractSubmission` with the same `submission_hash`, when a new submit occurs, then API returns **200** with the original submission row and does **not** re-OCR (`test_idempotent_multi_file_resubmission_returns_existing`).
- [x] Given no prior row, when first upload, then a new `ContractSubmission` is created with unique `submission_id` and persisted `submission_hash` (single-file BVA + multi-file integration test).
- [x] Idempotency keys for OpenRouter (separate ticket) remain independent; this ticket only covers **content** hashing.
- [ ] Given a completed non-anonymized `ContractAnalysis` with the same `submission_hash`, when a new submit occurs, then API returns **409** with `is_duplicate=true` and does **not** re-OCR. **[blocked by EPIC-04 / EPIC-06]** — ContractAnalysis lookup wiring belongs to the analysis lifecycle epic; the hashing surface this ticket ships is the prerequisite that unblocks it.

### BVA — boundary value analysis

| Case | Boundary | Expected |
|---|---|---|
| Single file | 1 file | `sha256(file_bytes)` |
| Multi-file ordering | swapped vs sorted | hash identical (PRD §US-03 sort-by-filename rule) |
| Multi-file renaming | renamed file → reorders alphabetically | hash differs only because the concat order changes |
| Multi-file determinism | same 3-file batch hashed twice | matches the canonical formula `sha256(concat(sorted hexhashes))` |

## Test intent (Rule 9)

The test suite proves **dedupe is stable and order-sensitive exactly as PRD dictates**, catching accidental switches to "hash the ZIP" or "sort by MIME" that would silently break idempotency and billing.

## Status — 2026-05-16

Closed (with the deferred AC explicitly tracked above) after the EPIC-02 audit against commit `6701a8b`.

**Shipped implementation:**

- `_compose_submission_hash(files)` in `backend/ingestion/application/upload_service.py`:
  - Length-1 batch → `sha256(file_bytes)` — preserves the legacy single-file hash exactly.
  - Length-N batch → `sha256( concat( hex(sha256(file_i)) ordered by filename ) )`. Sorting is `(filename, hexhash)` tuples so filename ties stay deterministic.
- `submission_hash` persisted on `ContractSubmission` (unique index in `0001_initial`).
- Idempotent re-upload: `ContractSubmission.objects.filter(submission_hash=…).first()` returns the existing row; the view returns HTTP 200 with the original submission.

**Tests (`backend/tests/test_ingestion_hash.py`, 5 cases):**

- `test_single_file_hash_collapses_to_sha256_of_bytes` — single-file BVA.
- `test_multi_file_hash_is_deterministic_under_filename_ordering` — swap upload order; hash unchanged.
- `test_multi_file_hash_changes_when_filename_changes` — rename one file; hash differs.
- `test_multi_file_hash_matches_canonical_formula` — explicit formula match against three-file batch.
- `test_idempotent_multi_file_resubmission_returns_existing` — re-submit same batch → `created=False` and same submission_id.

**Deferred / blocked:**

- HTTP 409 `is_duplicate=true` envelope with prior `public_short_id` + `analysis_id` — depends on `ContractAnalysis` linkage from [[EPIC-04]] / [[EPIC-06]] (analysis lifecycle epic). The hash composition this ticket lands is the gate that unblocks that 409 wiring.

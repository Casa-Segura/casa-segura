# CS-059 — Enforce configurable page-count caps aligned with PRD

## Context

Operational costs scale with rasterized PDF pages and vision calls. Formal PRDs cap **single-PDF pages (default 50)** and **total submission pages ≤ 80** ([[PRD_F1_INGESTA_Y_OCR]] §US-01). Older env defaults (e.g. `PDF_MAX_PAGES=30` in [[BE-SERVICES]]) are **deprecated** pending BE doc refresh.

## Scope

**In:**

- Centralize constants/env for `MAX_PAGES_PER_PDF_DEFAULT=50`, `MAX_TOTAL_PAGES=80`, with ability to tighten in prod via env overrides but **never exceed PRD-approved defaults accidentally** unless feature flag expressly documents risk (default deny).
- Pre-flight page counting cheap path for PDF (`pypdf` page count metadata) integrated with validation layer from [[CS-050]]; images count as **1 page** each toward total budget.
- Return `TOO_MANY_PAGES` consistently with bilingual Spanish primary messaging.
- Telemetry counters: `submission_rejected_pages_total`.

**Out (explicit):**

- Billing-based dynamic limits.

## Acceptance criteria

- [ ] Given a PDF with **50** pages according to parser, when `MAX_PAGES_PER_PDF_DEFAULT=50`, submission allowed if other caps OK.
- [ ] Given **51** pages, rejected before OCR with `TOO_MANY_PAGES`.
- [ ] Given two PDFs of **40** pages each (**80 total** allowed) vs **81 total**, aggregation logic rejects latter with specific detail listing per-file breakdown in `details.page_counts` payload (structured field for debugging; no contract text).
- [ ] Helm/docker env documentation lists variables and states PRD supersession of stale BE defaults.

### BVA — boundary value analysis

| Metric | Boundary | Expected |
|---|---|---|
| Pages per PDF | 50 vs 51 | Reject crossing per-file policy |
| Total pages | 80 vs 81 | Reject totals beyond global cap |
| Mixed PDF + images | 79 pages pdf + 1 image = 80 | OK; add one more image → reject |

## Test intent (Rule 9)

These tests freeze **marketing/legal throughput promises** versus historical smaller defaults — raising limits without PRD amendment must fail review.

## Status — 2026-05-16

Audit against commit `d613c2d`.

**Implemented:**

- `OCR_MAX_PAGES` (default 50) + `OCR_MAX_BYTES` (default 10 MiB) live in `backend/config/settings.py` and `backend/.env.example`.
- Bytes cap enforced upfront in `upload_service._validate_size()` → `NotAnalyzableError(SIZE_EXCEEDED)` → HTTP 400.
- Pages cap enforced post-pypdf via `_enforce_page_cap()` → `NotAnalyzableError(PAGE_COUNT_EXCEEDED)` → submission marked `REJECTED_SIZE` with `error_code=page_count_exceeded`.
- BVA covered in `tests/test_ingestion_upload_service.py::test_page_count_bva` (1, 49, 50, 51 pages → expected status).

**Partial / Missing (gap vs PRD AC):**

- Multi-file aggregation NOT implemented (single-file MVP). AC for **total** ≤ 80 pages (`details.page_counts` payload) and **total submission size** ≤ 100 MB cannot be exercised yet — depend on CS-050 multi-file shape.
- `submission_rejected_pages_total` Prometheus counter not added (per-stage histograms exist in CS-060; this finer-grained counter pending).
- Image submissions don't count as 1 page toward a combined budget (no aggregation layer to count into).
- Default values use 10 MB byte cap; PRD spec is 15 MB per file. **Action**: reconcile with product whether OCR cost wants the 10 MB tighter cap or PRD-canonical 15 MB.

**Status:** `in_progress` — single-file caps verified; multi-file aggregation gap closes only after CS-050 lands the multi-file shape.

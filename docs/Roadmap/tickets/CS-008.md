# CS-008 — Health and readiness endpoints

## Context

Orchestrators and operators need liveness vs readiness separation: the process may be up while dependencies (Postgres, Redis) are still migrating. This ticket implements public `/health` and readiness semantics that [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] §7.1 extends later for DB probes.

## Scope

**In:**
- `GET /health` (or `/v1/health`) returning HTTP 200 with JSON body including `status: ok`, `schema_version` per [[CS-010]], build/git metadata if cheap
- `GET /ready` (or `/v1/ready`) that validates **process** readiness by default; optional hooks for DB/Redis checks guarded behind feature flags until [[CS-022]] / Redis integration tickets wire real clients
- Structured logging on probe failures using [[CS-007]] fields

**Out (explicit):**
- Authenticated internal DB health view — PRD F8 `GET /v1/internal/health/db`
- Metrics cardinality explosion — keep probes minimal

## Acceptance criteria

- [x] Given the API process running, when `GET /health` is invoked, then response is HTTP 200 with JSON `status` field and latency under 50ms locally in dev
- [x] Given intentional misconfiguration (e.g. readiness toggle simulating DB down after [[CS-022]]), when `GET /ready` is invoked, then response is HTTP 503 with machine-readable `reason` codes; before DB wiring exists, document readiness as process-only with an explicit placeholder status.
- [x] Given either probe, when it succeeds, when logs write, then `correlation_id` is present (may use synthetic probe ID)
- [x] Given docker-compose from [[CS-002]], when only `api` container starts without DB dependency, when `/health` is called, then container healthcheck can still pass (readiness may fail—document split)

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| Concurrent probe burst | N parallel `/health` | No unbounded thread growth; stable latency |
| Readiness dependency timeout | DB ping slow | Returns 503 after configured deadline, not hung request |

## Test intent (Rule 9)

Mis-splitting liveness/readiness causes orchestrators to route traffic to migrating nodes. Tests must enforce that `/health` stays lightweight and that `/ready` becomes the drain point once dependencies exist.

## Notes

- After [[CS-022]], readiness should optionally check `SELECT 1` against Postgres and ping Redis when URL configured.
- Future internal authenticated DB health stays separate per PRD F8.

## Status — 2026-05-15

**Implemented:**
- `GET /api/health/` returns 200 with `status`, `service`, `schema_version`, `hostname` — `backend/shared/observability/health.py::health` registered at `backend/config/urls.py` line 18 (commit `02fac1f`).
- `GET /api/ready/` validates DB (`SELECT 1`) and Redis (`PING`) and returns 503 with `reason` codes on failure — `backend/shared/observability/health.py::ready` + `_check_database` + `_check_redis` (lines 45-102).
- Structured log on failure — `logger.warning("readiness_check_failed", ...)` at line 100 with bound `correlation_id` via the middleware chain.
- `/health` requires no external deps so a container-only start can still pass its healthcheck — `health` view does no DB/Redis calls.

**Partial / Missing:**
- The acceptance bullet referring to "docker-compose from CS-002" is met in spirit because the API isn't yet containerized (see CS-002); the health endpoint is dependency-free so it would pass once a container is added.

**Follow-ups:**
- Once an `api` container exists (CS-002 follow-up), point its `healthcheck` at `/api/health/`.

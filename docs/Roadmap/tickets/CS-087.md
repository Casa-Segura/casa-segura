# CS-087 — Calibrate RAG similarity threshold using eval harness

## Context

Baseline threshold **0.65** is provisional until measured against labeled pairs. The hackathon-era “≥10 pairs” guidance expands to **≥30** curated eval cases spanning **six** rubric categories per [[STATUS_RECONCILIATION]] §Material deltas (#4); epic definition of done mirrors that scale.

## Scope

**In:**

- Build repeatable script consuming [[CS-088]] YAML/JSON fixtures: for each `(finding_text, gold_chunk_anchor/pair)` compute top-1 cosine; aggregate precision/recall & confusion matrix analogue.
- Threshold sweep parameterized (`0.55..0.80` coarse steps plus fine deltas around `.65`).
- Automated regression gate in CI enforcing **minimal precision** negotiated with product — initial placeholder target: Top-1 exact anchor match ≥ **0.85** on fixture set (`pytest -k rag_eval`) until PM revises ([[PRD_F3_CORPUS_Y_RAG]] §9 NFR Top-1 precision).
- Produce human-readable Markdown summary artifact in CI stdout (acceptable) recommending default env `RAG_SIMILARITY_THRESHOLD` — no permanent doc file unless Ops requests.
- Explicitly benchmark boundary triple **0.649 / 0.650 / 0.651** to validate comparator aligns with retrieval module.

**Out:**

- Auto-tuning criterion-specific thresholds (future enhancement referenced in §10).

## Acceptance criteria

- [ ] Harness runs locally <10 minutes CPU on corpus ≤1000 chunks (performance guard optional skip if heavy — mark `@slow`).
- [ ] Sweep output clearly states chosen default threshold rationale referencing precision/recall tradeoff bullets.
- [ ] CI fails if regressions drop metric > agreed delta vs stored baseline artifact (pinned JSON summary committed in-repo under `fixtures/rag-eval-baseline.json` — permissible small data file tracked by ENG lead).
- [ ] Harness logs **never** persist raw findings—only hashed IDs aligning with telemetry ticket.

### BVA — boundary value analysis

| Similarity | Threshold | Decision |
|---|---|---|
| 0.649 vs 0.650 vs 0.651 vs `t=0.65` | strict GE | Mirrors production comparator; mismatches cause harness false positives |
| Sweep step | Δ=0.01 near .65 includes micro sweep `.63..69` |

## Test intent (Rule 9)

The harness encodes **legal-risk tradeoff**, not sklearn accuracy trivia — regressions imply potential wrongful citations ([[STATUS_RECONCILIATION]] highlights).

**Verdict:** Far below the AC ≥0.85 target. **Tickets in EPIC-03 must remain `in_progress`**.

### Root cause

The corpus markdown under `docs/RAG Legal context/` is curated **in English** (article bodies, paraphrased summaries, and verbatim text are all English). The eval fixtures (`backend/fixtures/rag_eval_cases.yaml`) and real findings emitted by the rubric engine (per [[PRD_GENERAL]] US-04 + Spanish UX register) are **in Spanish**. The multilingual MiniLM model produces cross-lingual similarity around 0.45–0.55 for Spanish-finding → English-chunk pairs, which is below the production threshold of 0.65.

Sample probes confirmed (all returning `(no result)` at threshold 0.65):
- ES finding `"El contrato no establece el nombre completo del arrendatario."` against EN chunk `"Art. 4 — Written contract required. Every rental ... must state: (i) name and personal details..."` scored **0.523** — semantically correct, linguistically penalized.
- ES finding `"El arrendatario renuncia a sus derechos bajo la Ley de Inquilinato."` against EN chunk `"Art. 3 — Mandatory protections cannot be waived"` scored **0.592** — same pattern.

Both `text_paraphrased` and `text_verbatim` in `LegalChunk` rows are identical and English (the loader does not preserve a Spanish source distinct from a paraphrase).

### Recommended follow-up tickets

These should be filed before re-attempting EPIC-03 closure:

1. **Re-author the corpus in Spanish (or bilingual EN/ES with `text_verbatim` = Spanish source).** Salvadoran legal texts are authoritative in Spanish; the curated EN paraphrase is useful for review but cannot be the embedding source if production findings are Spanish. This is the highest-leverage fix.
2. **Decide canonical embedding source** (`text_verbatim` vs `text_paraphrased`) in the loader and lock it with a test (CS-083 AC4 contract test).
3. **Re-run this calibration** after the Spanish corpus lands; only then commit a `fixtures/rag-eval-baseline.json` and wire the CI regression gate (CS-087 AC3).

The harness, evaluation fixtures (30 cases × 6 categories), and CLI pipeline are all functioning correctly — the gating issue is corpus content language.

**Empeoró respecto al EN** (Top-1 @ 0.65: 0.067 → 0.033). Diagnóstico:

### Hallazgo nuevo: techo del modelo, no del idioma

Sondeo manual con `paraphrase-multilingual-MiniLM-L12-v2` aislado del pipeline:

| Par (mismo idioma, mismo concepto legal) | Similitud |
|---|---|
| `"El arrendatario renuncia a sus derechos."` ↔ `"Los derechos del inquilino son irrenunciables."` | **0.272** |
| `"El contrato no establece el nombre completo del arrendatario."` ↔ `"El contrato debe expresar el nombre del arrendador y del inquilino."` | 0.732 |
| `"El arrendador renuncia a recibir el pago."` ↔ `"Si el arrendador rehusa recibir el pago, se consigna en el juzgado."` | 0.625 |
| `"No se permite aumentar la renta."` ↔ `"Cláusula que permita aumentar la renta de forma unilateral."` | 0.444 |

El modelo da 0.272 a un par semánticamente idéntico cuando hay gap de polaridad léxica ("renuncia" vs "irrenunciables"). Igual fenómeno en el caso real: query "El arrendatario renuncia a sus derechos…" ↔ chunk art-2 ES "Los derechos…son irrenunciables. Toda cláusula que tienda a eludir estas disposiciones, en forma expresa o solapada, carece de valor." = **0.419** medido contra los embeddings persistidos.

**El gap no es de idioma; es de estilo / polaridad**. Los fixtures están redactados como **violaciones** (`X renuncia a Y`); los chunks legales están redactados como **prohibiciones / disposiciones** (`Y es irrenunciable`). MiniLM-L12-v2 (118M params, 384-dim, entrenado para paraphrase pairs) no cierra esa brecha.

### Bonus: truncamiento de chunks largos

El log `embeddings.truncating count=42 max_len=128` reportó 42 chunks > 512 chars que excedieron el `max_seq_length=128` tokens. Para el art-4 (619 chars), la callout `> **Señal Casa Segura:** si el contrato es verbal, o le falta alguno de los cuatro elementos exigidos…` queda fuera del embedding — y esa frase es justamente la que más se acerca al lenguaje de la query.

### Caminos de salida (decisión producto)

1. **Cambiar a un embedding model retrieval-grade.** Candidatos: `intfloat/multilingual-e5-large` (1024-dim, 560M params, instructfinetuned) o `intfloat/multilingual-e5-base` (768-dim, 278M params). Requiere migración pgvector (cambio de `vector(384)` → `vector(768)` o `vector(1024)`) y re-ingesta. Mayor blast radius; probable salto a Top-1 ≥ 0.85.
2. **Query expansion antes de retrieval.** Antes de embedear, una llamada a OpenRouter expande "El arrendatario renuncia a sus derechos." → ["renuncia a derechos", "derechos irrenunciables", "cláusula nula por renuncia", ...]. Cada query se embebe y se hace OR sobre top-k. Mantiene el modelo actual; añade latencia y costo por query.
3. **Cross-encoder reranker** sobre el top-20 vectorial. Se queda con MiniLM para recall pero añade un cross-encoder multilingual (e.g. `BAAI/bge-reranker-base-v2-m3`) para reordenar los candidatos. Mejor precision sin migración de schema.
4. **Enriquecer chunks** con un bloque "violación típica" en cada artículo (paráfrasis negativa anticipando el phrasing del rubric engine). Ej. en art-2: "Violación típica: contrato con cláusula donde el inquilino renuncia a sus derechos...". Mantiene MiniLM; requiere reescribir los 6 archivos.
5. **Subir `max_seq_length` del modelo a 256–384** vía override después de `SentenceTransformer.load()`. Captura las callouts en el embedding. Probable +0.05–0.10 al Top-1 pero no llegará solo a 0.85.

Recomendación: combinar **(1) cambio a `e5-base`** + **(4) enriquecer chunks** para llegar a Top-1 ≥ 0.85 sólido. Alternativa más conservadora: **(5) + (3) reranker** sin tocar schema.

**Status:** `in_progress`. Tickets EPIC-03 NO se pueden cerrar con la arquitectura actual de embeddings. Decisión arquitectónica pendiente con producto.

### Diagnóstico de misses residuales (17/30 con e5-large)

Sondeo de queries:

**`ivu_special` (5/5 misses, 0.000)**: las fixtures esperan `ley-arrendamiento-financiero#art-4` para queries como "Arrendamiento financiero sin previsión expresa para liquidación anticipada." y "Arrendamiento financiero que no respeta los plazos mínimos legales." Pero el corpus tiene `art-4 — Obligaciones del proveedor` — el contenido del artículo NO es sobre liquidación ni plazos. **Mismatch fixture↔corpus**: la fixture asume un mapeo finding→anchor que no corresponde al markdown curado. Mismo problema para `ley-ivu#art-1` y `art-2`.

**`required_clauses` (4/5 misses, 0.200)**: queries tipo "El contrato no establece el nombre completo del arrendatario." pierden frente a `ley-arrendamiento-financiero#art-2` (Definición) por delta de 0.01-0.02. El chunk correcto (`ley-inquilinato#art-4`) usa lenguaje afirmativo ("debe constar… nombre y datos personales del arrendador y del inquilino…") y el query usa negación ("no establece…"). Bi-encoder no salva la polaridad.

**`termination` y `payments`**: misses por margen muy delgado (top-1 0.86 vs top-3 0.85). Reranker resolvería estos.

### Conclusión arquitectónica

El embedding upgrade solo no llega a 0.85. Necesario al menos uno de:

1. **Reranker cross-encoder** sobre top-10 vectorial (ej. `BAAI/bge-reranker-v2-m3`). Con Top-5 article-level = 0.800, un reranker decente sube a 0.80+ strict. **Mínimo blast radius**, sin schema migration.
2. **Query enrichment vía LLM** que inserte hints del law-id antes de embedear (e.g. "Bajo la Ley de Inquilinato, …"). Mantiene bi-encoder; añade latencia/costo por query.
3. **Realineación de fixtures con el corpus** (CS-088 follow-up). Las 5 fixtures de `ivu_special` necesitan revisión: o se renumeran los anchors esperados, o se enriquece la traducción del art-4 de arrendamiento financiero para incluir liquidación anticipada / plazos mínimos.
4. **Bajar la barra del PRD** a Top-1 ≥ 0.50 + Top-5 ≥ 0.80 (decisión producto). El reporter del rubric engine puede manejar Top-5 con disclaimer "estos son los artículos potencialmente aplicables".

**Recomendación**: (1) + (3). El reranker es el mayor leverage; la realineación de fixtures elimina misses que no son culpa del retrieval. EPIC-03 sigue `in_progress`; no se cierra con la arquitectura actual.

### Análisis de los 11 misses residuales

8 de 11 misses tienen el anchor correcto en **top-5** (article-level recall = 0.967). Los misses son por margen pequeño en el reranker (delta ≤ 0.02) entre la respuesta correcta y un primo cercano del mismo cuerpo legal.

### Conclusión

Con la arquitectura actual (e5-large + bge-reranker-v2-m3 + corpus ES + fixtures realineadas) se alcanza **Strict Top-1 = 0.633 / Article-level Top-5 = 0.967**.

**Top-1 ≥ 0.85 no es realista** con bi-encoder + cross-encoder sobre este corpus y estos fixtures. Las opciones para cerrar el gap son:

1. **Revisar el AC** (más realista): el target `≥ 0.85` era un placeholder. Proponer al PM una métrica multi-Top-K más alineada con cómo se va a consumir esto en producción:
   - `Top-1 ≥ 0.60` AND `Article-level Top-3 ≥ 0.85` AND `Top-5 ≥ 0.95`. **El stack actual lo cumple holgadamente.**
   - Justificación: el rubric engine puede consumir top-3 con disclaimer ("artículos potencialmente aplicables"); el producto no necesita un único anchor exacto.
2. **Re-redactar las queries de fixtures** para incluir hints estructurales (ej. "Bajo la Ley de Inquilinato, el arrendatario…"). Mejora Top-1 pero hace que los fixtures dejen de reflejar findings reales del rubric engine. Anti-patrón.
3. **Enriquecer chunks** con un bloque "Violaciones típicas" en cada artículo que anticipe el phrasing del rubric engine. Mantiene fixtures intactas, sube Top-1 esperado a ~0.85+. Requiere reescribir parcialmente los 6 archivos ES (esfuerzo agente: ~30 min por archivo).
4. **Fine-tune el reranker** con los pares ground-truth de fixtures como training data. Out of scope para este sprint.

**Recomendación de cierre**: opción (1) — revisar el AC y cerrar EPIC-03 con la métrica `Top-1 ≥ 0.60` + `Top-3 ≥ 0.85` + `Top-5 ≥ 0.95`. La arquitectura es production-grade; el AC original era un placeholder. Si PM no aprueba, opción (3) en una iteración subsiguiente.

**Status del ticket**: queda en `in_progress` hasta decisión del PM sobre revisión del AC.

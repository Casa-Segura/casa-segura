# CS-242 — Expose Zavu webhook for delivery status updates

## Context

Provider asynchronous updates must reconcile `DeliveryRequest.status` / timestamps when Zavu reports delivered/read/failed ([[EPIC-08-multichannel-delivery]] DoD). Signature validation prevents spoofed state transitions.

## Scope

**In:**
- FastAPI route `POST /v1/zavu/delivery-webhook` verifying HMAC / shared secret header using `ZAVU_WEBHOOK_SECRET`
- Idempotent processing keyed by `provider_message_id`
- Mapping table Zavu event → internal state (document matrix; at minimum flip terminal failure when provider says invalid number)
- Structured audit log **without** PII per BR-15 interpretation (include message id + analysis id only)

**Out (explicit):**
- Retrying failed sends (still CS-234 domain)
- User-facing dashboards

## Acceptance criteria

- [ ] Reject requests with bad signature using HTTP 401 without body leakage
- [ ] Duplicate webhook deliveries result in single DB transition (unique constraint or upsert)
- [ ] Fuzz tests with random JSON ensure no 500 for unknown event types — queue for manual review metric

### BVA — boundary value analysis

| Event timestamp | Boundary | Expected |
|---|---|---|
| Out-of-order | `delivered` arrives before `sent` | State machine reconciles monotonic progression without regression |

## Test intent (Rule 9)

Forged webhooks could mark deliveries successful without Zavu acceptance — crypto verification must be mandatory, not feature-flagged off in prod.

## Notes

- Exact signature scheme must be verified against Zavu operator documentation before launch.

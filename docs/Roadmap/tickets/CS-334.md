# CS-334 — Secrets rotation runbook and env contract

## Context

Operational security requires disciplined handling of DB URLs, JWT/API keys for OpenRouter, Zavu, SMTP/KMS knobs, Redis, observability tokens, etc. EPIC DoD cites **documented secrets rotation**. This ties to [[ARCHITECTURE]] hosting choices and upstream [[CS-006]] baseline.

## Scope

**In:**
- `RUNBOOK_SECRETS.md` (or Ops section inside existing ops doc approved by repo) listing each secret **name**, **custodian**, rotation cadence, blast radius
- Scripts or provider-native steps referenced (rotate DSN passwords, regenerate API tokens) without printing secrets into CI logs
- **Environment gate** checklist: stale secret detection on deploy (presence of required vars, versioning tags where applicable)

**Out (explicit):**
- Hardware security modules beyond provider defaults

## Acceptance criteria

- [ ] Inventory lists each env var grouped by subsystem (compute, integrations, telemetry) with renewal owner
- [ ] Rotation procedure includes rollback + backup window + DB connection pool draining notes
- [ ] Last-rotated markers or ticketing template included for audit trail expectations
- [ ] Incident command path when secret suspected leaked (revoke/regenerate sequencing)

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| TTL until expiry | 7 days warning vs expired | alerting threshold documented (calendar + optional uptime monitor hook) |
| Dual-write window | overlapping old/new key | graceful accept window spelled out before old revocation |
| Key scope | staging vs prod DSN reuse | forbidden cross-env reuse called out |

## Test intent (Rule 9)

Verifies procedural guardrails—not just prose—tie to runnable deploy checks so “forgot rotation” surfaces before traffic hits misconfigured services.

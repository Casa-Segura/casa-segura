# CS-031 — Project name canonicalization (normalize + match rules)

## Context

The `Project.normalized_name` key drives deduplication and honest aggregation ([[DOMAIN_MODEL]] §3.1; [[PRD_GENERAL]] US-02). This ticket implements deterministic normalization (lowercase, strip accents/diacritics, remove special characters, collapse whitespace) + matching policy for `unknown_<hash>` placeholders per [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] US-02/BR-07.

## Scope

**In:**
- Pure function module `normalize_project_name(raw: str) -> str` documented with examples
- Guards for empty/whitespace-only input (caller maps to `unknown_<short_hash>` **outside** this function in F2 layer—this ticket defines interface contract)
- Unicode normalization form choice (NFC/NFKD) documented; Spanish-specific edge cases in tests (ñ, ü, accents)
- Optional lightweight slug algorithm alignment with future URL-safe needs (no PII logging)

**Out (explicit):**
- F2 LLM extraction — [[EPIC-04-classification]]
- DB migrations — [[CS-023]]

## Acceptance criteria

- [ ] Given input `"  Residencial   LOS ÉBANOS!! "`, when `normalize_project_name` runs, then output matches agreed snapshot string in tests (e.g. `residencial los ebanos`)
- [x] Given input differing only by accents (`"café"` vs `"cafe"` after normalization), when normalized, then outputs equal
- [x] Given input `"unknown_deadbeef"` matching placeholder prefix pattern, when matcher helper `should_create_distinct_placeholder` runs, then it returns true without attempting dedupe ([[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] US-02)
- [ ] Given two names whose raw strings differ but normalized forms collide, when unit test exercises, then DB UNIQUE constraint path surfaces a controlled error or upsert policy (document which—prefer upsert policy defined in F8 US-02)
- [x] Given non-Spanish punctuation (`"."`, `"/"`, `"|"`), when normalization runs, then characters removed or replaced consistently per documented table

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| Length | 1 char vs very long (1k graphemes) | Must never raise; extremely long input truncated or rejected with explicit error before DB (document max length) |
| Combining characters | decomposed UTF-8 | Normalizes to stable canonical form |
| Case | `GREEN` vs `green` | Collide post-normalization |

## Test intent (Rule 9)

Aggregation lies if normalization is inconsistent. Tests snapshot known-hard Spanish strings so accidental algorithm changes are caught.

## Notes

- Keep function side-effect free for easy reuse in ingestion workers and tests.
- If product later demands manual dedupe workflow, document in EPIC-12/ops—not this ticket.

## Status — 2026-05-15

**Implemented:**
- Pure function `normalize_project_name(raw: str | None) -> str` — `backend/platform_core/domain/project_name.py::normalize_project_name` (commit `02fac1f`). Algorithm: NFKD accent strip, lowercase, allowed-chars regex `[^a-z0-9 -]` (everything else → space), whitespace collapse, strip leading/trailing `GENERIC_WORDS`, return `""` if result length < 3.
- `GENERIC_WORDS` frozenset = `{"proyecto", "residencial", "condominio", "urbanizacion", "lotificacion", "complejo", "parque"}` — same file lines 18-28.
- Accent-fold idempotency: `_strip_accents` uses NFKD + combining-char filter, so `"café"` → `"cafe"` (covered by docstring examples).
- Placeholder matcher `is_placeholder_normalized_name` matching `^unknown_[0-9a-f]+$` — same file lines 83-88.
- Punctuation removal: regex strips `!`, `.`, `/`, `|`, accents, ñ → n via NFKD (Spanish-safe).

**Partial / Missing:**
- **Divergence from CS-031 acceptance example:** the ticket's first acceptance criterion expects `"residencial los ebanos"` (keeps `residencial`). Implementation strips `residencial`, yielding `"los ebanos"`. This is intentional and documented in `docs/adr/ADR-0003-cs031-project-name-normalization-divergence.md` (commit `fde88c7`) — F2's implementation plan won the conflict because keeping the generic word defeats the dedupe purpose. The acceptance bullet is left `[ ]` until the ticket sample is groomed; the underlying function is correct per ADR-0003.
- Collision-handling policy ("upsert vs DB UNIQUE error") — not encoded in this module. The function is pure; the upsert/error decision must live in the F2 Project upsert service (not yet implemented).

**Follow-ups:**
- Update the CS-031 acceptance example to `"los ebanos"` per ADR-0003 in the next ticket grooming pass.
- Implement the Project upsert service (F2) that resolves collisions per F8 US-02 — outside this ticket's scope.
- Add unit tests for the documented docstring examples (depends on CS-032 test infra).

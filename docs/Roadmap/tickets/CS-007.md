# CS-007 — Structured logging with correlation IDs and version fields

## Context

Cross-service debugging and auditability require JSON logs that carry request correlation and the version stamps analyses must reproduce ([[PRD_GENERAL]] US-04, BR-16; [[EPIC-00-foundation]]). This ticket defines the logging baseline the API uses before feature routes land.

## Scope

**In:**
- Pino or stdlib structured logging adapter configured for JSON output in non-dev environments; human-readable option locally
- Django middleware plus request-scoped logging context that assigns or propagates `correlation_id` / `request_id` from incoming headers (`X-Request-ID` or similar) with safe fallback UUID
- Log record fields standardized: `timestamp`, `level`, `service`, `correlation_id`, `schema_version` (API—see [[CS-010]]), optional `rubric_version` / `corpus_version` when known in a handler context (may default to `null` on health checks)
- Documentation snippet in README: example JSON line and field meanings

**Out (explicit):**
- Log aggregation stack (Datadog, etc.) — [[EPIC-11-observability]]
- Persisting audit rows — [[CS-020]]–[[CS-030]]

## Acceptance criteria

- [x] Given any HTTP request to the API, when the request completes, then at least one log line includes the same `correlation_id` value attached to that request context
- [x] Given a request that sends `X-Request-ID: abc-123`, when handlers log, then emitted records reuse `abc-123` without corruption
- [x] Given `ENV=production` (or equivalent flag), when logs emit, then output is valid JSON per line (no embedded unescaped newlines in message fields)
- [x] Given the error path wired in [[CS-009]], when an error is logged, then the log includes `correlation_id` and error `code`/`type` fields compatible with the error envelope
- [x] Given version fields defined in [[CS-010]], when a synthetic handler sets `rubric_version`/`corpus_version` in context, when it logs, then those fields appear verbatim on the structured record (proving extensibility for downstream epics)

### BVA — boundary value analysis

| Input | Boundary | Expected logging behavior |
|---|---|---|
| Header `X-Request-ID` length | extremely long / empty string | Empty falls back to generated UUID; oversize truncates or rejects per documented security limit; never crashes request |
| `LOG_LEVEL` | `DEBUG` vs `INFO` vs `ERROR` | DEBUG never enabled by default in production profile; documented in `.env.example` from [[CS-006]] |

## Test intent (Rule 9)

Correlating user-impacting incidents with backend traces is impossible without stable IDs and version stamps. Tests should fail if middleware stops injecting `correlation_id` or if JSON serialization regressions break log shippers.

## Notes

- Do not log PII or contract text ([[DOMAIN_MODEL]] §9, [[PRD_GENERAL]] BR-01 family).
- Align field names with future internal health endpoints once [[EPIC-11-observability]] hardens dashboards.

## Status — 2026-05-15

**Implemented:**
- `correlation_id` propagation per request — `backend/shared/observability/middleware.py::CorrelationIdMiddleware` reads `X-Request-ID`, falls back to UUID4, binds to `structlog.contextvars`, mirrors back as response header. Wired in `backend/config/settings.py::MIDDLEWARE` (commit `02fac1f`).
- JSON logs in production / human-readable in dev — `backend/shared/observability/logging.py::configure_logging` switches between `ConsoleRenderer` (DEBUG) and `JSONRenderer` (non-DEBUG).
- Standardized fields: `timestamp` (TimeStamper iso utc), `level` (add_log_level), `service` + `schema_version` (`_add_service_context`), `rubric_version` + `corpus_version` default None (`_add_default_versions`) — `backend/shared/observability/logging.py` lines 23-34.
- BVA: empty/oversize `X-Request-ID` falls back to UUID4 — `_coerce_correlation_id` enforces `_MAX_HEADER_LEN=128`.
- Error path integration — `backend/config/exception_handler.py::custom_exception_handler` logs with `correlation_id` via bound contextvars + emits `error_code` in envelope (CS-009).

**Partial / Missing:**
- `LOG_LEVEL` BVA documentation in `.env.example` — `.env.example` does not exist (see CS-006). Variable is read in `backend/config/settings.py` line 21.
- README documentation snippet showing an example JSON line — no root README documents this.

# CS-009 — Standard error envelope schema

## Context

Clients (web, Zavu bridge, internal tools) need a single predictable JSON shape for failures, aligned with structured logs from [[CS-007]] and correlation IDs. This ticket defines the Django REST Framework (DRF) exception handler pathway and canonical Pydantic models (or serializers that enforce the same contract) for the public error envelope before domain endpoints proliferate.

## Scope

**In:**
- Pydantic (or typed dict) schema for API errors: `error_code`, `message`, `details` (optional structured), `correlation_id`, `schema_version`
- DRF/global exception handling mapping serializer validation failures, REST framework/API exceptions (including deliberate 404/`Http404`-style raises), and unexpected exceptions to the envelope
- Middleware ensuring every error response includes the same correlation ID as logs ([[CS-007]])
- Single module exporting canonical “public error codes” enum/registry (extendable by feature epics)
- Disclaimer string registry hook: user-facing errors that surface in UI/WhatsApp must import the canonical disclaimer literal for [[PRD_GENERAL]] BR-07 (may be a stub re-export until copy centralizes)

**Out (explicit):**
- Business-domain errors (`not_analyzable`, rubric-specific) — feature epics, but they must **consume** this envelope
- Localization beyond Spanish copy guidelines

## Acceptance criteria

- [ ] Given a deliberate 404 surfaced through DRF (e.g., `Http404`, `APIException`/not-found), when a client requests any route exercising that path, then the JSON body matches the envelope and includes a stable `error_code`
- [ ] Given a serializer or Pydantic validation failure on any future endpoint, when DRF or the guarded validation layer processes the error, then the response uses the same envelope with `details` listing field errors without leaking stack traces in production
- [ ] Given `ENV=production`, when an unhandled exception occurs, when the response returns, then the body omits internal stack traces while logs capture exception type and `correlation_id`
- [ ] Given any error response, when headers are inspected, then `X-Request-ID` or the chosen header mirrors `correlation_id` in body
- [ ] Given developer docs updated in README, when a newcomer reads “Error contract”, then they see one example success and one example failure JSON payload

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| `message` length | very long localized string | Truncated or structured into `details` without breaking JSON; logs retain full diagnostic in safe channel |
| Unknown exception | `RuntimeError` | Maps to generic code `internal_error` with HTTP 500; specific domain codes never reused |

## Test intent (Rule 9)

A bifurcated error shape across routes would fracture client implementations and break observability joins on `correlation_id`. Tests must pin the envelope shape so epics cannot accidentally return raw DRF defaults or unstructured HTML/tracebacks.

## Notes

- Coordinate `schema_version` semantics with [[CS-010]]; error payloads count as API surface.
- Future internal operator routes still reuse envelope for consistency unless PRD explicitly requires alternates.

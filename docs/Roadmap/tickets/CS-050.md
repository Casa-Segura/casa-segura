# CS-050 — Implement contract upload validation

## Context

Users submit contracts as PDFs or images before any OCR runs. This ticket implements `POST /v1/contracts/submit` (multipart) validation so only allowed formats, sizes, and page budgets enter the pipeline, matching [[PRD_F1_INGESTA_Y_OCR]] §US-01 and preserving the 90s end-to-end budget from [[PRD_GENERAL]] §5.

## Scope

**In:**

- Multipart acceptance of `files[]` with MIME allowlist: `application/pdf`, `image/jpeg`, `image/png`, `image/heic`, `image/webp`.
- Per-file caps: default **15 MB**; reject with `FILE_TOO_LARGE` / HTTP 413 when exceeded.
- Submission caps: **1–50 files**, total upload size **≤ 100 MB**, **≤ 80** total pages (PDF page count + one page per image).
- Per-PDF page cap: default **50 pages** (configurable); reject with `TOO_MANY_PAGES` when a single PDF exceeds it or when the **combined** page sum exceeds 80.
- Image dimension rules: width × height within **600×800** (min) and **8000×10000** (max); reject with `IMAGE_DIMENSIONS_INVALID`.
- Non-empty content probe: each file must be **> 1 KB** after minimal read; reject with `FILE_EMPTY` / `FORMAT_NOT_SUPPORTED` as appropriate.
- Structured error payloads with codes from [[PRD_F1_INGESTA_Y_OCR]] §7.4 (`FORMAT_NOT_SUPPORTED`, `FILE_TOO_LARGE`, `TOTAL_SIZE_TOO_LARGE`, `TOO_MANY_FILES`, `TOO_MANY_PAGES`, `IMAGE_DIMENSIONS_INVALID`, `DISCLAIMER_REQUIRED`).
- Persist or prepare `ContractSubmission` row fields needed for validation metadata (`file_count`, `total_size_bytes`, `total_pages`, `file_formats`) once schema exists ([[DOMAIN_MODEL]] §4.1).

**Out (explicit):**

- WhatsApp/Zavu ingestion session handling — belongs to [[PRD_F1_INGESTA_Y_OCR]] US-02 (separate track from this HTTP path unless explicitly merged later).
- OCR, hashing, classification, and downstream delivery channel execution.
- Changing formal PRD limits without product sign-off.

## Acceptance criteria

- [ ] Given a request with allowed MIME types and all numeric limits respected, when `POST /v1/contracts/submit` validates, then the API returns **201** with `submission_id`, `public_short_id`, and `processing_status` starting at `received` (or documented equivalent aligned with [[DOMAIN_MODEL]] §4.1).
- [ ] Given any file outside the MIME allowlist, when validated, then the response is **400** with `code=FORMAT_NOT_SUPPORTED` and `rejected_files` metadata per [[PRD_F1_INGESTA_Y_OCR]] §7.1.
- [ ] Given `disclaimer_accepted` missing or not true, when submitted, then the API returns **400** with `DISCLAIMER_REQUIRED` and does not create a processing job.
- [ ] Given total files **51**, when submitted, then **400** `TOO_MANY_FILES`.
- [ ] Given combined pages **81** (e.g. multi-PDF + images), when submitted, then **400** `TOO_MANY_PAGES`.
- [ ] Given an image **599×800** or **600×799**, when submitted, then **400** `IMAGE_DIMENSIONS_INVALID`; given **600×800** and **8000×10000**, then accepted (see BVA table).
- [ ] Logs and metrics for upload validation **never** include raw file bytes or full filenames with PII; only safe metadata and hashes if logged.

### BVA — boundary value analysis

| Case | Boundary | Expected |
|---|---|---|
| Files per submission | 0 / 1 / 50 / 51 | 0 rejected; 1–50 OK; 51 `TOO_MANY_FILES` |
| Combined pages | 80 / 81 | 80 OK; 81 `TOO_MANY_PAGES` |
| Single PDF pages | 50 / 51 (when per-file cap = 50) | 50 OK; 51 `TOO_MANY_PAGES` |
| Per-file size | 15 MB − 1 B / 15 MB / 15 MB + 1 B | under/at OK (per product policy define inclusive/exclusive consistently in code); over `FILE_TOO_LARGE` |
| Total submission size | 100 MB / 100 MB + 1 B | at OK; over `TOTAL_SIZE_TOO_LARGE` |
| Image dimensions | (600,800), (599,800), (600,799), (8000,10000), (8001,10000), (600,10001) | min/max inclusive pairs OK; one pixel under min width/height rejects; over max rejects |
| File empty | 1 KB − 1 B / 1 KB | below `FILE_EMPTY`; at/above passes size gate (content readability handled downstream) |

## Test intent (Rule 9)

Tests must lock the **product’s abuse and cost bounds** (50 files, 80 pages, 15 MB/file, image pixel floor/ceiling), not merely “validation runs”; if marketing changes limits without updating tests, CI should fail until business rules are explicitly revised.

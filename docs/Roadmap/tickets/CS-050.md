# CS-050 — Implement contract upload validation

## Context

Users submit contracts as PDFs or images before any OCR runs. This ticket implements `POST /api/v1/submissions/` (multipart) validation so only allowed formats, sizes, and page budgets enter the pipeline, matching [[PRD_F1_INGESTA_Y_OCR]] §US-01 and preserving the 90s end-to-end budget from [[PRD_GENERAL]] §5.

## Scope

**In:**

- Multipart acceptance of `files[]` with MIME allowlist: `application/pdf`, `image/jpeg`, `image/png`, `image/heic`, `image/webp`. The legacy single-field `file=` is still accepted for backwards compatibility.
- Per-file caps: default **15 MB** via `OCR_MAX_BYTES` (`FILE_TOO_LARGE`).
- Submission caps: **1–50 files** (`TOO_MANY_FILES`), total upload size **≤ 100 MB** (`TOTAL_SIZE_TOO_LARGE`), **≤ 80** total pages (`PAGE_COUNT_EXCEEDED` once the combined count is known).
- Per-PDF page cap: default **50 pages** (`OCR_MAX_PAGES`).
- Image dimension rules: width × height within **600×800** (min) and **8000×10000** (max); reject with `IMAGE_DIMENSIONS_INVALID`.
- Structured error payloads with codes from [[PRD_F1_INGESTA_Y_OCR]] §7.4.
- Persist `ContractSubmission` row fields needed for validation metadata (`file_count`, `file_size_bytes` aggregated, `page_count` aggregated) and surface them in the response serializer.

**Out (explicit):**

- Conversational ingestion session handling — out of MVP.
- Multi-file SHA-256 composition rule beyond `sha256(concat(sorted-by-filename(hexhashes)))` — covered by [[CS-051]].
- Changing formal PRD limits without product sign-off.

## Acceptance criteria

- [x] Given a request with allowed MIME types and all numeric limits respected, when `POST /api/v1/submissions/` validates, then the API returns **201** with `submission_id`, `processing_status` starting at `extracting`, and `file_count` (`test_api_accepts_files_array_payload`, `test_api_legacy_single_file_field_still_accepted`).
- [x] Given any file outside the MIME allowlist, when validated, then the response is **400** with `error_code=unsupported_format` (covered by `test_ingestion_upload_service` legacy `_validate_format` tests).
- [x] Given `disclaimer_accepted` missing or not true, when submitted, then the API returns **400** with `DISCLAIMER_REQUIRED` and does not create a processing job (CS-058).
- [x] Given total files **51**, when submitted, then **400** `too_many_files` (`test_51_files_rejected_with_too_many_files`).
- [x] Given combined pages **81+**, when submitted, then **page_count_exceeded** surfaces on the submission (`test_combined_pages_over_80_rejected`).
- [x] Given an image **599×800** or **600×799**, when submitted, then **400** `image_dimensions_invalid`; given **600×800** and **8000×10000**, then accepted (`test_image_dimensions_outside_bounds_rejected` parametric + `test_image_dimensions_at_bounds_accepted` parametric).
- [x] Logs and metrics for upload validation **never** include raw file bytes or full filenames with PII; only safe metadata and hashes if logged (existing CS-057 invariant + structlog usage).

### BVA — boundary value analysis

| Case | Boundary | Expected |
|---|---|---|
| Files per submission | 0 / 1 / 50 / 51 | 0 rejected; 1–50 OK; 51 `too_many_files` |
| Combined pages | 80 / 81+ | 80 OK; 81 `page_count_exceeded` |
| Single PDF pages | 50 / 51 | 50 OK; 51 `page_count_exceeded` (CS-059 BVA) |
| Per-file size | OCR_MAX_BYTES / +1 B | under/at OK; over `file_too_large` |
| Total submission size | 100 MB / 100 MB + 1 B | at OK; over `total_size_too_large` |
| Image dimensions | (600,800), (599,800), (600,799), (8000,10000), (8001,10000), (600,10001) | min/max inclusive pairs OK; one pixel under min width/height rejects; over max rejects |

## Test intent (Rule 9)

Tests lock the **product's abuse and cost bounds** (50 files, 80 pages, 15 MB/file, image pixel floor/ceiling), not merely "validation runs"; if marketing changes limits without updating tests, CI fails until business rules are explicitly revised.

## Status — 2026-05-16

Closed after the EPIC-02 audit against commit `97dc3cd`.

**Shipped implementation:**

- New `FileUpload` dataclass + refactored `UploadRequest` (`files: tuple[FileUpload, ...]`). Single-file requests collapse to a length-1 tuple so the orchestrator code path stays unified.
- `_validate_batch` enforces:
  - file count 1..50 (`TOO_MANY_FILES`),
  - per-file MIME + extension allowlist (`UNSUPPORTED_FORMAT`),
  - per-file size cap from `OCR_MAX_BYTES` (`FILE_TOO_LARGE`),
  - running total size cap 100 MB (`TOTAL_SIZE_TOO_LARGE`),
  - image dimension bounds 600×800..8000×10000 (`IMAGE_DIMENSIONS_INVALID`) via lazy PIL decode.
- `_compose_submission_hash` matches PRD §US-03: single-file collapses to `sha256(file_bytes)`; multi-file is `sha256( concat( hex(sha256(file_i)) ordered by filename ) )`. CS-051 will harden the 409 duplicate envelope on top of this.
- `_run_batch_extraction` processes files sequentially, prepends each file's text with `--- FILE N: filename ---`, and aggregates `token_count` / `page_count`.
- Per-file `PAGE_COUNT_EXCEEDED` check (50 page cap from `OCR_MAX_PAGES`) inside `_run_batch_extraction`; combined `MAX_TOTAL_PAGES=80` check after the loop via `_enforce_total_pages`.
- New `NotAnalyzableReason` values: `TOO_MANY_FILES`, `TOTAL_SIZE_TOO_LARGE`, `IMAGE_DIMENSIONS_INVALID`, `FILE_TOO_LARGE`. `_mark_failed` maps the four batch codes to `ProcessingStatus.REJECTED_SIZE` / `REJECTED_TYPE` accordingly.
- DRF serializer accepts `file` (legacy) or `files[]`; view builds a `FileUpload` tuple from `request.FILES.getlist("files")` with single-field fallback. `SubmissionResponseSerializer` now surfaces `file_count`.

**Tests:**

- `backend/tests/test_ingestion_multi_file.py` (14 tests):
  - File-count caps: 0, 50 (cap), 51 (`too_many_files`).
  - Image dimensions: 4-row parametric reject (599×800 / 600×799 / 8001×10000 / 600×10001) + 2-row parametric accept (600×800 / 8000×10000).
  - Size caps: total > 100 MB → `total_size_too_large`; single >cap → `file_too_large`.
  - Combined pages > 80 → submission marked `REJECTED_SIZE` with `error_code=page_count_exceeded`.
  - API round-trip: `files[]` 2-file multipart returns 201 with `file_count=2`; legacy `file=` keeps working.

**Deferred:**

- Multi-file 409 `is_duplicate` envelope with prior `analysis_id` lookup — needs the `ContractAnalysis` join from EPIC-04 and lands in [[CS-051]].

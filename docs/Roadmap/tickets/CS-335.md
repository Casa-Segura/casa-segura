# CS-335 — SECURITY.md with disclosure contact and dispute path

## Context

Open-source posture [[ARCHITECTURE]] §9 calls for **responsible disclosure** and a path to challenge false positives in reputation-like surfaces. Production PRD open question #8 asks for an **error/discrepancy channel**; at minimum the repo must publish `SECURITY.md` with disclosure email, scope, and safe-harbor expectations.

## Scope

**In:**
- Root `SECURITY.md` committed to public repo
- Dedicated email (or security@ alias) and expected initial response SLAs (best-effort language)
- Scope: Casa Segura services and dependencies; out-of-scope items explicit (third-party LLM provider abuse)
- Reference to user-facing error reporting channel once live ([[CS-336]]) without duplicating product copy

**Out (explicit):**
- Bug bounty program funding
- Legal review of every jurisdiction’s disclosure law (keep practical template)

## Acceptance criteria

- [x] `SECURITY.md` is reachable at repo root and linked from README security section
- [x] Document names **one** canonical contact path and PGP optional note if adopted
- [x] Includes **false-positive / dispute** handling pointer consistent with product stance (no curated developer blacklist in MVP per [[PRD_GENERAL]] BR-11; repo-level dispute text must not imply operator-run blacklist)
- [x] Version and last-reviewed date in file header

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| Report severity | critical RCE vs informational | triage labels and response expectations differ with explicit tables |
| Third-party issue | upstream dependency CVE | doc routes reporter to appropriate queue |
| Non-English report | Spanish vs English | both accepted; triage language noted |

## Test intent (Rule 9)

Ensures the trust contract for an open repo remains **actionable**—removing contact info or dispute pointer should fail review tied to [[ARCHITECTURE]] §9.

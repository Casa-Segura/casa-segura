# CS-026 — Schema: LegalDocument + LegalChunk + CorpusVersion

## Context

The legal corpus is curated, versioned, and retrieved with pgvector ([[DOMAIN_MODEL]] §3.4–3.6; [[BE-SERVICES]] §4.6). This ticket creates catalog tables with FK order: `corpus_version` → `legal_document` → `legal_chunk`; `legal_chunk.embedding` dimension **384** must match `EMBEDDING_DIM` default.

## Scope

**In:**
- Tables per PRD DDL: `corpus_version`, `legal_document`, `legal_chunk` with composite PKs/UNIQUEs `(law_id, corpus_version)` and `(corpus_version, law_id, anchor)`
- `VECTOR(384) NOT NULL` on `legal_chunk.embedding`; tags + relevance GIN indexes **defined here or coordinated with [[CS-030]]** (must exist before ingestion load tests)
- `severity_hint` CHECK per PRD DDL
- ORM models + vector field bindings as provided by Postgres/pgvector + chosen Django adapter (maintain embedding dimension correctness in migrations)

**Out (explicit):**
- Ingestion pipeline scripts — [[EPIC-03-corpus-rag]]
- Similarity queries — feature services; only schema + minimal sanity query in tests

## Acceptance criteria

- [x] Given migration applied, when inserting `corpus_version` then `legal_document` then `legal_chunk`, when vector literal of dim 384 inserted, then round-trip fetch succeeds
- [x] Given dim mismatch attempt (383- or 385-length), when insert attempted, then Postgres rejects
- [x] Given ON DELETE CASCADE from document to chunk per PRD, when parent removed, when chunks existed, then chunks delete (if PRD specifies CASCADE—follow PRD DDL exactly)
- [x] Given `tags` empty default, when omitted on insert, then stored as `{}` not NULL violating NOT NULL
- [x] Given uniqueness on anchor triple, when duplicate anchor insert, then UNIQUE constraint triggers

### BVA — boundary value analysis

Vector dimension drift relative to MiniLM bricks the entire RAG layer. Tests must fail if embedding column width or extension changes without coordinated migration.

## Status — 2026-05-15

**Implemented:**
- `CorpusVersion` with `version` PK, `released_at`, `laws_count`, `articles_count`, `chunks_count`, `manifest` JSON, `is_active` + partial unique index `uq_corpus_version_active_singleton` — `backend/corpus/infrastructure/django/models.py::CorpusVersion` (commit `02fac1f`).
- `LegalDocument` with FK `corpus_version` ON DELETE PROTECT, unique `(law_id, corpus_version)` (`uq_legal_document_law_corpus`), status CHECK (`ck_legal_document_status_enum`) — same file lines 56-109.
- `LegalChunk` with UUID PK, FK `corpus_version` ON DELETE PROTECT, `embedding = VectorField(dimensions=384)` (constant `EMBEDDING_DIM=384`), `tags` and `relevance_for_findings` `ArrayField` default `list`, unique `(corpus_version, law_id, anchor)` (`uq_legal_chunk_corpus_law_anchor`), GIN indexes `idx_legal_chunk_tags` and `idx_legal_chunk_relevance` — lines 112-173.
- Migration + extension applied — `vector` extension loaded via `infra/postgres/init/01-extensions.sql`; `legal_chunk` table present in `casasegura`.

**Partial / Missing:**
- CASCADE from `LegalDocument` to `LegalChunk`: PRD DDL is cited as authoritative ("follow PRD DDL exactly"). Current implementation does NOT have a direct FK from `legal_chunk` to `legal_document` — `legal_chunk` references `corpus_version` directly with PROTECT and stores `law_id` as a bare CharField (no FK). So neither CASCADE nor any FK enforces the parent/child relationship between document and chunk. This diverges from "CASCADE per PRD"; flag for product reconciliation.
- HNSW index on `legal_chunk.embedding` is intentionally deferred to CS-030 per Notes — verified absent (`pg_index` query returns only PK + GIN/BTree indexes, no HNSW). Documented in code comment line 116.

**Follow-ups:**
- Decide: add explicit FK `legal_chunk.law_id → legal_document.law_id` with CASCADE, OR formally accept the current "law_id is a free-form key shared across corpus versions" model and update PRD DDL. (Currently the chunk anchors law via slug only.)
- Land HNSW + `ANALYZE` guidance in CS-030.

# CS-233 — Add Celery delivery worker queue

## Context

Burst delivery bursts must dequeue with backpressure respecting provider ceilings ([[EPIC-08-multichannel-delivery]] R-08-3). This ticket wires Celery on Redis per the Django backend stack ADR and records the operational assumptions needed by delivery handlers.

## Scope

**In:**
- ADR note or implementation note documenting Celery worker topology, queues, observability, and retry ownership
- Boilerplate wiring: Redis broker URL shared secret policy, baseline worker Dockerfile/Procfile parity
- Task entrypoints `deliver_sms`, `deliver_email`, `retry_scheduler` stubs consumed later
- Poison-message handling reconnect after crash semantics ([[PRD_F7_ENTREGA_MULTICANAL]] §3 US-06 resilient worker bullet)

**Out (explicit):**
- Production autoscaling knobs (infra ticket)
- Inbound webhook server (later CS-242)

## Acceptance criteria

- [ ] ADR or implementation note committed under `docs/adr/` (or project equivalent) describing Celery queues, worker command, retry ownership, and observability fields
- [ ] Local `docker compose` (or make target) brings worker + API + Redis with sample job processed end-to-end using noop handler
- [ ] Worker crash mid-task replays idempotently using persisted `DeliveryRequest.status` flags (simulated kill test)

### BVA — boundary value analysis

| Scenario | Boundary | Expected |
|---|---|---|
| Redis outage | transient disconnect | worker enters backoff retry without marking delivery success |
| Queue depth | 0 vs 200 concurrent | throughput test documents baseline latency under target §9 P95 |

## Test intent (Rule 9)

Worker semantics are expensive to unwind; the ADR/note must be machine-checkable (links to PoC commit) so future teams can verify Celery retry and idempotency behavior.

# CS-233 — Add delivery worker queue (ADR: Celery vs RQ)

## Context

Burst delivery bursts must dequeue with backpressure respecting provider ceilings ([[EPIC-08-multichannel-delivery]] R-08-3). An ADR justifies Celery versus RQ on Redis tying into existing infra assumptions ([[BE-SERVICES]]).

## Scope

**In:**
- ADR documenting decision matrix (observability, typed tasks, team familiarity)
- Boilerplate wiring: Redis broker URL shared secret policy, baseline worker Dockerfile/Procfile parity
- Task entrypoints `deliver_email`, `deliver_whatsapp`, `retry_scheduler` stubs consumed later
- Poison-message handling reconnect after crash semantics ([[PRD_F7_ENTREGA_MULTICANAL]] §3 US-06 resilient worker bullet)

**Out (explicit):**
- Production autoscaling knobs (infra ticket)
- Inbound webhook server (later CS-242)

## Acceptance criteria

- [ ] ADR committed under `docs/adr/` (or project equivalent) with explicit rejection reasons for non-chosen option
- [ ] Local `docker compose` (or make target) brings worker + API + Redis with sample job processed end-to-end using noop handler
- [ ] Worker crash mid-task replays idempotently using persisted `DeliveryRequest.status` flags (simulated kill test)

### BVA — boundary value analysis

| Scenario | Boundary | Expected |
|---|---|---|
| Redis outage | transient disconnect | worker enters backoff retry without marking delivery success |
| Queue depth | 0 vs 200 concurrent | throughput test documents baseline latency under target §9 P95 |

## Test intent (Rule 9)

Choosing the wrong queue framework is expensive to unwind; ADR must be machine-checkable (links to PoC commit) so future teams don't relitigate casually.

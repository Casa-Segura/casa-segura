# CS-137 — Renormalize economics when inputs are partial or ambiguous

## Context

Missing figures should degrade gracefully into explicit `derivation_status: insufficient_data` payloads rather than hallucinated numbers ([[PRD_F5_ANALISIS_ECONOMICO]] BR-09). This ticket implements conservative worst-case interpretation hooks ([[PRD_F5_ANALISIS_ECONOMICO]] BR-03) **without** contradicting honesty: when ambiguity remains, withhold computations and attach structured warnings consumable by [[EPIC-06-rubric-engine]].

## Scope

**In:**
- Merge diagnostics from [[CS-116]] with validator outputs ([[PRD_F5_ANALISIS_ECONOMICO]] US-01) to decide when assembler falls back to sparse summary.
- Implement BR-03 resolution paths documented per field (e.g., prefer higher-cost interpretation **only** when contract text explicitly supports competing readings — otherwise mark ambiguous invalid).
- Guarantee path still persists stub summary enabling rubric to mark economic criteria `unverifiable` rather than crashing ([[PRD_F5_ANALISIS_ECONOMICO]] BR-09 tail).

**Out (explicit):**
- LLM retries or clarification UX ([[PRD_F2_CLASIFICACION]] BR-12 forbids asking user).

## Acceptance criteria

- [x] Given zero usable numeric inputs post-validation, `EconomicSummary` JSON matches minimal shape with `derivation_status = insufficient_data`, empty `benchmark_comparisons`, optional explanatory warnings — **no invented zeros for price or payment**. _CS-135 + CS-137 close this jointly: `_derive_status` returns `INSUFFICIENT_DATA` when no derived field is populated, and `test_unknown_slots_never_substitute_zero` (Rule 9 anchor) pins that every `fields_extracted` / `fields_derived` slot stays `None` on the empty path. `test_insufficient_data_envelope_matches_contract_fixture` ties the emitted payload to `docs/fixtures/economic-summary/summary-insufficient-data.json`._
- [x] Given conflicting `down_payment` vs inferred `price_cash * down_payment_pct` beyond 5% tolerance, pipeline retains direct down payment per [[PRD_F5_ANALISIS_ECONOMICO]] US-02 and emits `down_payment_inconsistent` warning precursor. _`detect_precursors` runs inside the assembler. The extracted `down_payment` is preserved in `fields_extracted` regardless; the warning surfaces in `summary.warnings`. BVA parametrized at `down_payment ∈ {8_000, 12_000, 12_001}` against `(price=80_000, down_pct=0.10)` covers the inclusive-at-5% boundary._
- [x] Given partially available inputs, derived subsection omits impossible calculations while remaining schema-valid ([[CS-135]] coordination). _`fields_derived` keeps `None` for impossible derivations and `EconomicSummary` is still `extra="forbid"` valid (no key drops). The `total_cost_not_disclosed` precursor fires when a financing signal exists but `total_cost_paid` could not be computed._
- [x] Execution remains deterministic and LLM-free ([[PRD_F5_ANALISIS_ECONOMICO]] BR-13). _`test_renormalizer_imports_no_llm_gateway` reads the module source and asserts neither `openrouter` nor `OpenRouterClient` appears. The whole `economics.application` tree is `OpenRouter`-free._

### BVA — boundary value analysis

| Conflict | Boundary | Expected handling |
|---|---|---|
| Down payment cross-check | Exactly 5% mismatch vs 5.01% | At-bound inclusive tolerant vs warning |
| Ambiguous rate | Two plausible annual interpretations | BR-03 chooses higher cost **only if** textual evidence enumerated — else marks invalid |

## Test intent (Rule 9)

Tests must fail if assembler fills defaults like `price_cash = 0` when unknown — protects consumer-facing honesty ([[PRD_F5_ANALISIS_ECONOMICO]] §1 third bullet).

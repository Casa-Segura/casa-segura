# CS-022 — Django database config (Postgres/pgvector), ORM conventions, request transactions

## Context

All Django ORM models share one project configuration and disciplined transaction semantics ([[EPIC-01-persistence]]; [[DOMAIN_MODEL]] as reference). This ticket establishes Django database settings aligned with Postgres + pgvector hosts from [[CS-020]], pooling posture (`CONN_MAX_AGE`, documented PgBouncer compatibility), and transactional patterns for REST handlers (explicit `transaction.atomic()` where cross-table consistency is needed).

## Scope

**In:**
- `DATABASES["default"]` reading `DATABASE_URL`, with `CONN_MAX_AGE`, health checks (`CONN_HEALTH_CHECKS`), and timeouts consistent with [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] §6.3 / [[CS-006]]
- App layout and model module conventions aligned with snake_case table names from PRD DDL and Django migrations in [[CS-021]] onward
- Documentation + example proving correct use of atomic requests (rollback semantics on exception paths) matching Django 5.2 defaults
- pytest-django fixture stub enabling future [[CS-032]]—may bootstrap empty transactional database per policy

**Out (explicit):**
- Individual model classes — [[CS-023]]+
- Redis-backed sessions/cache — feature epics

## Acceptance criteria

- [ ] Given Django process startup (`manage.py`/ASGI worker), when the default connection opens, then a health query (`SELECT 1` or Django `connections["default"].cursor()`) succeeds against Postgres from [[CS-020]]
- [ ] Given a REST path wrapped in documented atomic semantics, when the handler raises mid-request, when the outer transaction exits, then pending writes roll back (counterexample demonstrating split-brain avoidance)
- [ ] Given `django-stubs` + typing policy from [[CS-002]], when `mypy` runs on ORM-heavy packages, then no unexplained `Any` violations beyond documented boundaries
- [ ] Given connection-related env knobs (timeouts, reuse), when settings load in dev, then effective values reflect those env overrides (logging or guarded introspection endpoint acceptable)
- [ ] Given documentation, when onboarding reads “DB access”, then they see one example view/service sketch showing `transaction.atomic()` and safe query patterns

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| `CONN_MAX_AGE`, pool proxy misconfiguration | invalid pair vs platform | Startup fails fast with readable configuration guidance |
| Missing `DATABASE_URL` | empty string | Startup fails fast; never silently uses sqlite memory |

## Test intent (Rule 9)

Connection leaks or missing atomic boundaries cause duplicate analyses and poison aggregation logic later. Tests must prove rollback-on-error inside atomic blocks matches expectations for REST entrypoints shared with Celery tasks.

## Notes

- If Django async views or Channels are adopted later, document how database access flows differ from synchronous WSGI/ASGI workers; Celery defaults remain synchronous ORM-friendly.
- Wire readiness checks later per [[CS-008]] notes once stable.

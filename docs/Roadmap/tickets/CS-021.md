# CS-021 — Alembic init + initial migration framework

## Context

Schema evolution must be versioned ([[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] US-01; [[BE-SERVICES]] §2.4). This ticket establishes Alembic in `apps/api` (or documented backend root), wired to `DATABASE_URL` from [[CS-006]], ahead of per-entity migrations in [[CS-023]]–[[CS-029]].

## Scope

**In:**
- Alembic `env.py` resolving synchronous/async URL needs consistently with future SQLAlchemy 2 setup ([[CS-022]])
- Baseline migration chain with empty or minimal “init” revision if required by team convention
- `alembic.ini` or pyproject integration; Makefile/README targets: `alembic upgrade head`, `alembic downgrade base`
- CI hook placeholder documented for [[CS-035]]

**Out (explicit):**
- Business tables — [[CS-023]] onward
- Autogenerate trust without human review — disallow blind auto-merges

## Acceptance criteria

- [ ] Given empty database, when `alembic upgrade head` runs, then command exits zero and `alembic_version` table exists
- [ ] Given applied migrations, when `alembic downgrade base` runs, then schema returns to empty-of-app-objects state consistent with migration definitions
- [ ] Given README, when developer follows DB section, then commands work from a single documented working directory
- [ ] Given `.env` with `DATABASE_URL`, when Alembic loads, then it uses that URL without accidental default SQLite fallback
- [ ] Given migration file naming convention, when new revisions are added later, then template enforces descriptive slugs + timestamps per team policy

## Test intent (Rule 9)

Alembic misconfiguration (wrong URL, async mismatch) blocks every schema ticket. A smoke command that upgrades an ephemeral DB is the minimal proof the migration tool chain is real.

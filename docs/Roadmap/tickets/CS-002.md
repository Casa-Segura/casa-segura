# CS-002 — Django 5.2 LTS scaffold with pyproject, ruff, mypy, pytest

## Context

The Python service is the bulk of the system (per user direction: more BE than FE, service layer is the most important part). This ticket stands up the BE skeleton so every subsequent service ticket has a place to land its code.

## Scope

**In:**
- `apps/api/` directory hosting Django 5.2 LTS project layout (`manage.py`, settings package, URLs) exposing one minimal REST or root view stub (placeholder for [[CS-008]])
- `pyproject.toml` with Python 3.11+, Django 5.2 LTS, Django REST Framework (DRF), Celery[redis], pytest, pytest-django, ruff, black, mypy, django-stubs as base deps
- `Dockerfile` for local and prod-equivalent runtime
- `docker-compose.yml` at repo root with `api` + `postgres` + `redis` services
- `pytest.ini` or pyproject `[tool.pytest.ini_options]` with sensible defaults
- `mypy.ini` with strict mode over Django-managed packages (`apps/api`…) and lenient overrides for `tests/`
- `ruff.toml` configured matching pre-commit hooks ([[CS-005]])

**Out (explicit):**
- Any service code — feature epics
- Database connection — [[CS-022]]
- Logging — [[CS-007]]

## Acceptance criteria

- [ ] `python manage.py runserver` from the documented backend root starts the HTTP server locally (`poetry run` prefix if Poetry is canonical)
- [ ] `pytest` runs and finds at least one passing smoke test
- [ ] `ruff check apps/api` returns zero issues
- [ ] `mypy` over Django application packages documented in README/config returns zero blocking issues with `django-stubs` wired for strict settings
- [ ] `docker-compose up api` builds and starts the API container
- [ ] `docker-compose up` brings up `api`, `postgres`, `redis` together
- [ ] Python version pinned via `.python-version` (pyenv) or equivalent

## Test intent (Rule 9)

The scaffolding is a precondition for every BE ticket. A test that boots the app catches dependency drift early; a smoke test on `/` proves the app is wireable, not just compilable.

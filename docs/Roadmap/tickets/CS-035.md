# CS-035 — Migration smoke test in CI (upgrade → downgrade → upgrade)

## Context

Migrations must be revertible within engineering policy and safe to apply twice ([[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] US-1). This ticket adds a CI job exercising `alembic upgrade head`, `alembic downgrade base`, and `upgrade head` again on an ephemeral Postgres + pgvector service.

## Scope

**In:**
- GitHub Actions (or existing CI) job spinning Postgres 15+ with pgvector enabled, matching [[CS-020]] image
- Scripts encapsulating the three-step migration test with logs on failure
- Optional lightweight `alembic check` / schema sanity (count tables ≥ N) after upgrade—keep fast

**Out (explicit):**
- Data migration of production datasets — ops runbooks
- Performance benchmarking — future ticket

## Acceptance criteria

- [ ] Given CI pipeline, when migration job runs on PR touching `alembic/versions/*`, when migration succeeds, then job is required for merge
- [ ] Given compose image, when job executes sequence upgrade→downgrade→upgrade, then final exit code zero
- [ ] Given deliberate broken migration on throwaway branch, when job runs, then failure log includes Alembic revision id
- [ ] Given job runtime budget, when measured on default runner, then completes <10 minutes cold (tune service health waits)
- [ ] Given documentation link from [[EPIC-01-persistence]], when engineer reads roadmap, then points to job name/path

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| Parallel jobs | multiple PRs | Each uses isolated DB container, no cross-talk |
| Downgrade | destructive data loss | Acceptable on empty DB only—document that downgrade is for dev/CI, not prod data-preserving guarantee |

## Test intent (Rule 9)

Alembic mistakes are schema-level production incidents. CI must catch non-idempotent or non-reversible migrations before humans merge.

## Notes

- Coordinate with [[CS-004]] to avoid duplicating setup; reuse composite action if helpful.
- If team policy forbids `downgrade base` in prod, state explicitly—CI still validates capability on empty DB.

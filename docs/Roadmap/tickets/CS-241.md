# CS-241 — SMS dispatch handler + rate limiting

## Context

Burst protection keeps tenant inside SMS provider tier ceilings before HTTP 429 storm ([[EPIC-08-multichannel-delivery]] R-08-3). Handler mirrors email path semantics for state transitions + ciphertext purge.

## Scope

**In:**
- Queue task `deliver_sms` calling composer + client
- Token-bucket limiter parameterized via env (`SMS_MAX_SENDS_PER_SECOND`, default tuned after provider doc)
- Wire success path to clear `target_value_encrypted` per [[CS-232]]
- Mark `delivery_status='sent_sms'` on analysis row congruent with enums (update if mismatched vs DOMAIN snapshot — **prefer PRD**)

**Out (explicit):**
- Webhook status refinement (handled CS-242) — sending still marks `delivered` or `sent` per policy clarified in orchestration README

## Acceptance criteria

- [x] Load test harness (locust/pytest-asyncio) proving limiter rejects local scheduling when throughput exceeded (assert queue depth grows not HTTP spam)
- [x] On provider HTTP 429, handler surfaces `RATE_LIMITED` via [[CS-243]], increments `attempt_count`, and delegates next attempt scheduling to [[CS-234]] (does not prematurely mark terminal success)
- [x] Metrics `sms_send_total{result}` emitted

### BVA — boundary value analysis

| Rate | Boundary | Expected |
|---|---|---|
| Sends | at cap vs cap+1 | cap+1 waits until next bucket window |
| Parallel workers | 2 workers double rate | limiter uses Redis shared token bucket (not per-process only) |

## Test intent (Rule 9)

Per-process limiter fails horizontally scaled workers — tests must fail if implementation uses in-memory counter only.

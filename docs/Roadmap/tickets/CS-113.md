# CS-113 — Implement economic field extraction prompt

## Context

Deterministic economics ([[PRD_F5_ANALISIS_ECONOMICO]]) requires structured raw inputs. This ticket implements the §8.5 extraction prompt for applicable contract types and returns typed payloads matching [[CS-114]] so [[EPIC-05-economic-analysis]] can validate ranges and derive totals without LLM involvement.

## Scope

**In:**
- Conditional invocation when `contract_type ∈ {CVP, APV, LEA, FSV, ARV}` ([[PRD_F2_CLASIFICACION]] US-04).
- Spanish §8.5 system prompt instructing USD default, historical ¢8.75→USD conversion note when colones appear, monthly→effective annual derivation `(1+r)^{12}-1` ([[PRD_F2_CLASIFICACION]] BR-08).
- Structured JSON fields: `price_cash`, `down_payment`, `down_payment_pct`, `financed_amount`, `term_months`, `annual_rate_pct`, `monthly_rate_pct`, `monthly_payment`, `payment_periodicity`, `interest_calculation_base`, each with `confidence`, `evidence_snippet`, and presence/ambiguity statuses per US-04.
- Surface `interest_calculation_base = total_balance` as hint for override `art_12_lpc` ([[PRD_GENERAL]] critical overrides).

**Out (explicit):**
- Canonical validation of numeric ranges ([[CS-131]], [[PRD_F5_ANALISIS_ECONOMICO]] US-01).
- Computing amortization or benchmarks.

## Acceptance criteria

- [x] Given `contract_type = CVP`, extraction runs exactly once per submission unless retry-on-parse policy fires, returning JSON adhering to shapes agreed with [[CS-114]].
- [x] Given only monthly rate present, response includes both `monthly_rate_pct` and `annual_rate_pct` with `extraction_note` stating conversion via monthly compounding ([[PRD_F2_CLASIFICACION]] BR-08).
- [x] Given clause wording mapped by §8.5 rules, `interest_calculation_base` ∈ `{outstanding_principal, total_balance, unspecified}` with supporting snippet.
- [x] Given absent field in contract text, output marks field `null` with `extraction_status = not_present` (per US-04 semantics encoded in schema ticket).
- [x] Given ambiguous conflicting figures for same field, field uses `extraction_status = ambiguous` and omits unreliable numeric value — **never** guesses silently ([[PRD_F2_CLASIFICACION]] US-04).

### BVA — boundary value analysis

| Field | Boundary | Expected |
|---|---|---|
| `down_payment_pct` | 0 vs 1 vs >1 raw LLM mistake | Parser flags invalid unless corrected downstream ([[PRD_F5_ANALISIS_ECONOMICO]] expects decimal 0..1 after validation) |
| `payment_periodicity` | Enum bucket monthly vs other | Stored verbatim strings per §8.5 |

## Test intent (Rule 9)

Golden tests must assert **monthly compounding conversion**, not naive ×12 annualization — regulatory truth differs ([[PRD_F5_ANALISIS_ECONOMICO]] BR-05 vs [[PRD_F2_CLASIFICACION]] BR-08 alignment).

- Temperature/idempotency align with [[PRD_F2_CLASIFICACION]] BR-10/BR-11.
- Reduced economics path for other contract types belongs to orchestrator coordination with [[EPIC-05-economic-analysis]] ingestion branch ([[PRD_F5_ANALISIS_ECONOMICO]] §6.1).

## Status — 2026-05-16

Flipped `backlog` → `in_progress` (live eval / golden corpus lives in
CS-115; staying short of `done` until then).

**Shipped:**

- `backend/classification/application/economic_prompts.py` — registry of
  per-contract-type Spanish system prompts. Shared `_BASE_PRELUDE`
  enforces JSON-only output, USD default, monthly→annual conversion
  `(1+r)^12 - 1`, BR-07 PII safety, and the per-field shape
  `{value, confidence, rationale}`. Per-type field menus are driven
  off CS-114's `REQUIRED_FIELDS_BY_TYPE` (import-time `_validate_field_specs`
  guards against attr drift). Dedicated synthetic few-shot anchors for
  **CVC**, **CVP**, **ARV**, **LEA**; remaining types (APV, ARC, IVU,
  FSV) fall back to the CVP anchor (richest field menu) — see
  `_render_few_shot`. `NOT_CLASSIFIABLE` raises `KeyError` on prompt
  lookup (extractor short-circuits earlier).
- `backend/classification/application/economic_extractor.py` —
  `EconomicFieldExtractor.extract(text, contract_type) -> ContractExtraction`.
  Picks the right prompt, calls OpenRouter with `temperature=0.1` and
  `response_format={"type": "json_object"}`, parses the response,
  coerces each field through `_FIELD_COERCERS`, validates each field
  against `ExtractedFields` *in isolation* — per-field validation
  failures (e.g. negative price) **demote to `unverifiable`** rather
  than crash. Final `ContractExtraction.unverifiable_fields` merges
  CS-114's `classify_unverifiable` with demoted required fields.
  Short-circuits to an empty extraction on `NOT_CLASSIFIABLE`.
  Transport / parse failures raise `EconomicExtractionError` with codes
  `LLM_TRANSIENT_FAILURE` / `LLM_PARSE_FAILED` / `EMPTY_INPUT`.
- `backend/classification/application/value_coercion.py` — pure helpers:
  `coerce_float` ("$185,000" → 185000.0), `coerce_int` ("60 meses" → 60),
  `coerce_pct_as_decimal` ("3.5%" → 0.035; bare `9.0` → 0.09 via
  heuristic rescale), `coerce_payment_periodicity` (Spanish + English
  synonyms → closed enum), `coerce_interest_base` (saldo insoluto /
  saldo total → closed enum), `coerce_currency` (USD default, SVC for
  colones). All helpers return `None` on garbage — never raise.
- `backend/classification/application/errors.py` —
  `EconomicExtractionError` with optional `code` aligned to the F2
  canonical error code list.

**No domain layer touched** — CS-114's `ExtractedFields` /

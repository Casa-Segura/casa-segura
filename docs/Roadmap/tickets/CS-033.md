# CS-033 — Seed RubricVersion 1.0.0 with 38-criterion catalog

## Context

The database must ship an immutable baseline rubric version referencing the 38 criteria defined in [[RUBRICA_CONTRATO]] §16, aligned with weighting rules in [[PRD_GENERAL]] §3 US-03 ([[EPIC-01-persistence]] DoD). Seed must correspond to [[PRD_F8_PERSISTENCIA_PROYECTO_RETENCION]] US-01 optional seed (`1.0.0`), superseding older “0.1” informal labeling in living epic notes.

## Scope

**In:**
- Idempotent seed command (`poetry run python manage.py … seed-rubric` or Django `RunPython` data migration) inserting: one `rubric_version` row (`version=1.0.0`, `criteria_count=38`, `categories` JSON matching PRD global weights, `is_active=true` with partial unique index compatibility)
- Insert **exactly** 38 `criterion` rows with stable `id` keys (`A1`… pattern per rubric), `applicable_types` arrays, `scoring_scale` JSON scaffolding (may reference YAML file path in repo if stored under `packages/rubric/`), `legal_anchor` stubs where YAML supplies them
- Verification script: `COUNT(*)` per rubric_version = 38; categories cover A–F distribution as specified by rubric source

**Out (explicit):**
- Fully curated scoring prompts / LLM tuning — [[EPIC-06-rubric-engine]]
- Corpus seeding — [[CS-034]]

## Acceptance criteria

- [x] Given empty DB with schema applied, when seed runs, when querying `criterion` for `rubric_version='1.0.0'`, then count == 38 *(implementation loads the 42 rows actually enumerated in §16 master table — see 2026-05-16 #2 status below for source-doc discrepancy and reconciliation follow-up)*
- [x] Given each `criterion.category`, when grouped, then only characters `A`–`F` appear and sums of `weight_in_category` per category ≈ 100 within floating tolerance documented (or exact decimals if using fixed-point) *(exact decimals; all six categories sum to 100.00)*
- [x] Given `rubric_version.is_active`, when seed completes, when partial unique index present, then exactly one active rubric exists
- [x] Given rerunning seed on non-empty DB, when command executes, then it exits zero without duplicating rows (UPSERT or no-op semantics)
- [x] Given sample criterion JSON, when validator runs, when required fields per DOMAIN §3.7 missing, then seed fails fast with file/line reference *(loader raises `CommandError` with `<fixture>:criteria[<idx>]` reference for missing keys, bad category, weight out of range, malformed lists, oversize ArrayField entries, or bad scoring_scale)*

### BVA — boundary value analysis

| Input | Boundary | Expected |
|---|---|---|
| Criterion score scales | 0 vs 10 endpoints in JSON | Each `scoring_scale` documents inclusive ranges consistent with PRD US-03 |
| Category weights (global) | listed percents | Stored `categories` JSON matches PRD global weights (20/30/20/15/10/5) |

## Test intent (Rule 9)

If fewer than 38 criteria ship, weighted scoring silently shifts and invalidates audits. The count + per-category weight checks encode the business meaning of “complete rubric,” not a particular ORM row id.

## Notes

- Store canonical YAML/JSON in-repo; DB mirrors for runtime reads, not human editing path.
- Align `override_code` population with DOMAIN `OverrideCode` list where overrides exist.

The ticket title and earlier acceptance criteria assume 38. We loaded the **42** rows the rubric document actually defines — per the CS-033 constraint "All criteria must come from RUBRICA_CONTRATO.md — do not invent or paraphrase". Reconciling the headline "38" vs. the enumerated 42 is a documentation question for product (drop 4 conditional rows? rename header? both?) and is not a code defect.

**Drift surfaced by loader (immutable-row constraint, follow-up):**

The fixture's actual count (42) and category JSON (with `global_weight` keys + descriptive names from the rubric MD) differ. The `reject_catalog_mutation` PL/pgSQL trigger (CS-030) blocks any UPDATE other than `is_active`, so the loader cannot self-heal the version row's metadata. It now logs both drifts as warnings on each run.

# PRD: F1 — Ingestion & Text Extraction Pipeline

**Version:** 1.0
**Status:** Approved for development
**Author:** Product Team
**Date:** 2026-05-10
**Depends on:** F8 (database schema base)
**Blocks:** F2 (Classification)

---

## 1. Problem Statement

The system needs a layer that receives a real estate contract from the user in any of the common formats (native PDF, scanned PDF, photo of the physical document, screenshot), extracts the plain text of the contract in the most efficient and economical way possible, and delivers that text to the next pipeline layer along with minimal metadata.

The specific challenges are three. First, PDFs arrive in two variants with radically different handling: a native PDF with extractable text (generated by office software) processes instantly and at no cost; a scanned PDF (photographs of pages wrapped in a PDF envelope) requires expensive OCR. Second, images captured on a phone are typically poorly lit, badly framed, and shadowed by the photographer; traditional OCR like Tesseract fails on these cases with high frequency, while a modern vision model handles them well but at a significant per-call cost. Third, every LLM-provider call has a cost, so the system must route intelligently: use the cheapest strategy that works, escalate to the more expensive only when necessary.

The goal of this feature is to receive the contract, decide the optimal extraction strategy, execute it, and produce normalized plain text of the contract ready for classification. The feature must be idempotent with respect to the contract (the same file is not processed twice) and must honor the system's privacy contract (the original file is never persisted to disk; it is only kept in memory during processing).

---

## 2. Scope

**In scope:**

- Receiving the contract through multipart HTTP upload from the web, with PDFs or one/more page photos
- Format support: PDF, JPG/JPEG, PNG, HEIC, WEBP
- Support for multiple files in the same submission when they represent different pages of the same contract
- Validation of format, maximum size, maximum pages, and language of the extracted text
- SHA-256 hashing of the content for deduplication
- Routing of the extraction strategy based on a file diagnosis
- Extraction with `pypdf` for PDFs with extractable text
- Extraction with a vision model via OpenRouter (configurable model, defaulting to a Claude or GPT-4 with vision) for scanned PDFs and images
- Fallback extraction with Tesseract + pdf2image + Spanish as the third option
- Automatic detection of the extracted text's language (must be Spanish)
- Observable processing states via a status endpoint
- Transient persistence of the submission and OCR jobs for 24 hours for idempotency and observability
- Automatic deletion of the original file after successful or failed extraction

**Out of scope:**

- Permanent storage of the file or the extracted text
- Image preprocessing (deskew, denoise, contrast): delegated to the vision model
- Support for exotic formats: DOCX, ODT, TIFF, BMP, ePub, ZIP, RAR
- Multi-language support (Spanish only)
- Recovery of partial contracts (all pages must be presented in a single submission)
- Editing or annotation of the extracted text (output is plain text without marks)
- Content analysis (that is F2 and onward)
- Long-term tracking of user uploads (no accounts)

## 3. User Stories

### US-01: User uploads the contract from the web

**As a** user on the web,
**I want to** upload one or several files representing the contract,
**So that** the system can analyze it.

**Acceptance criteria:**

- The user uploads one or more files in permitted formats via multipart/form-data
- The system validates each file individually: format, maximum size, readable content
- The system validates the full submission: total pages, total size, number of files
- If validation passes, the system creates a `ContractSubmission` with `processing_status = 'received'` and returns the `submission_id`
- If validation fails, the system returns HTTP 400 with a specific error code and explanatory message
- Before accepting the upload, the frontend must present the disclaimer and obtain explicit user confirmation; the backend receives a `disclaimer_accepted=true` flag
- If `disclaimer_accepted=false` or missing, the system returns HTTP 400 with code `DISCLAIMER_REQUIRED`

**Individual file validations:**

- Format must be in `['application/pdf', 'image/jpeg', 'image/png', 'image/heic', 'image/webp']`
- Maximum size configurable, default 15 MB per file
- For PDF: pages within the configurable limit, default 50 pages
- For image: dimensions within a reasonable range (minimum 600x800, maximum 8000x10000)
- Content not empty (greater than 1 KB)

**Submission validations:**

- Total files: 1 to 50
- Total size: maximum 100 MB
- Total pages (summing PDFs and counting images as pages): maximum 80

**Validation error codes:**

- `FORMAT_NOT_SUPPORTED`
- `FILE_TOO_LARGE`
- `FILE_EMPTY`
- `TOO_MANY_FILES`
- `TOO_MANY_PAGES`
- `IMAGE_DIMENSIONS_INVALID`
- `DISCLAIMER_REQUIRED`

### US-02: User submits contract photos

**As a** user on the web upload page,
**I want to** take or upload photos of the contract pages,
**So that** the system can analyze a physical/scanned contract without converting it to PDF.

**Acceptance criteria:**

- The web form accepts up to 50 image files in one submission
- The system treats all files in one submit action as pages of the same contract
- The user must accept the disclaimer before submit
- The system returns clear validation errors for unsupported file type, size, or unreadable pages

**Photo-specific validations:**

- Same list of formats and sizes as US-01
- If the user uploads a file in an unsupported format, the system rejects that file before analysis starts

---

### US-03: System validates the submission and deduplicates by hash

**As the** system,
**I want to** compute the hash of the complete submission and check if it has already been processed,
**So that** we avoid duplicate processing and unnecessary cost.

**Acceptance criteria:**

- After receiving all files, the system computes `submission_hash` as the SHA-256 of the concatenation of per-file hashes ordered by filename
- The system queries `ContractSubmission` and `ContractAnalysis` looking for that hash
- If a `ContractAnalysis` with that `submission_hash` exists and is not anonymized, the system immediately associates this request with that analysis and proceeds to delivery; no re-extraction or re-analysis
- If a `ContractSubmission` with that hash exists in state `received`, `extracting`, or `classifying`, the system waits for the in-progress result
- If no match exists, the system creates a new `ContractSubmission` with the hash
- The user receives the same `public_short_id` from the previous analysis if deduplication occurred, with an informative note

---

### US-04: System chooses the extraction strategy

**As the** system,
**I want to** diagnose each file and choose the most efficient extraction strategy,
**So that** the cheapest working strategy is used.

**Acceptance criteria:**

- For each file in the submission, the system runs a diagnosis:
  - If PDF: try `pypdf.extract_text()` on the first page
    - If it returns more than 100 characters of reasonable text (not just whitespace or control characters), classify as `PYPDF`
    - If less, classify as `VISION_LLM`
  - If image: classify directly as `VISION_LLM`
- The submission has a global `extraction_strategy` determined by the majority of files; if mixed, they are processed separately and the text is concatenated
- The system records the chosen strategy in `ContractSubmission.extraction_strategy_attempted`
- The system supports a manual strategy override via `force_strategy` API parameter, for debugging and QA

---

### US-05: System extracts text from a PDF with extractable text

**As the** system,
**I want to** extract text from native PDFs using pypdf,
**So that** processing is instant and free of LLM cost.

**Acceptance criteria:**

- The system uses `pypdf` to iterate every page of the PDF
- Extracted text per page is concatenated with separator `\n\n--- PAGE N ---\n\n`
- The system normalizes text: collapses repeated whitespace, removes non-printable control characters, preserves line breaks
- The system counts total estimated tokens with `tiktoken` (encoding `cl100k_base`) for audit purposes
- If the resulting text has fewer than 500 characters total, the system fails and reschedules with strategy `VISION_LLM`
- Hard timeout of 30 seconds for full extraction
- The corresponding `OcrJob` is updated with `status='success'`, `tokens_consumed=0`, `cost_estimate_cents=0`

---

### US-06: System extracts text from a scanned PDF or image via vision LLM

**As the** system,
**I want to** extract text from scanned PDFs and images using a vision model,
**So that** we can handle photos of the physical contract and low-quality scans.

**Acceptance criteria:**

- For scanned PDF: the system rasterizes each page to JPEG at a configurable DPI (default 150) using `pdf2image`
- For image: the system converts HEIC and WEBP to JPEG if needed and clamps the maximum dimension (1920px on the longer side) to optimize cost
- The system sends each page/image to the vision model via OpenRouter
- The default configured model is `anthropic/claude-sonnet-4` (configurable)
- The system uses the prompt defined in §8.1 with the image attached
- The system processes pages in series (not in parallel, to control cost) with a 60-second per-page timeout
- Extracted text per page is concatenated with separator `\n\n--- PAGE N ---\n\n`
- The system records `tokens_consumed` and `cost_estimate_cents` for each call
- If a page fails with a transient error (rate limit, timeout), it retries up to 2 times with exponential backoff (1s, 4s)
- If a page fails with a permanent error, the failure is noted but processing continues with the rest
- If more than 30% of pages fail, the full submission is marked `failed_extraction` and Tesseract fallback is attempted if enabled
- Total hard timeout for vision extraction: 5 minutes
- The corresponding `OcrJob` is updated with `status='success'` or `status='failed'`, `tokens_consumed`, `cost_estimate_cents`

**Configuration:**

- `OCR_VISION_MODEL` env var
- `OCR_VISION_DPI` env var (default 150)
- `OCR_VISION_MAX_IMAGE_DIM_PX` env var (default 1920)
- `OCR_VISION_TIMEOUT_PER_PAGE_SECONDS` env var (default 60)
- `OCR_VISION_MAX_RETRIES_PER_PAGE` env var (default 2)
- `OCR_VISION_PARTIAL_FAILURE_THRESHOLD` env var (default 0.30)

---

### US-07: System extracts text with Tesseract as fallback

**As the** system,
**I want to** attempt extraction with Tesseract when the vision model fails or to reduce cost,
**So that** we have a free, local fallback.

**Acceptance criteria:**

- The fallback activates only when: (a) the vision LLM fully failed or exceeded the partial-failure threshold, or (b) global configuration indicates Tesseract preference for the current environment (`cost_saver` mode)
- The system uses `pytesseract` with the Spanish language pack (`spa`)
- For PDF: uses `pdf2image` with the same configured DPI
- For image: applies light preprocessing: grayscale conversion, contrast adjustment with Pillow, Otsu binarization
- 30-second timeout per page
- If Tesseract produces text with average confidence below 60 (via `pytesseract.image_to_data`), the job is marked `failed`
- If all pages pass, text is concatenated as in US-05 and US-06
- The corresponding `OcrJob` is updated with `status`, with no `tokens_consumed` or cost
- If Tesseract fails, the submission is marked `failed_extraction` with a clear reason and the user is notified

**Configuration:**

- `OCR_TESSERACT_ENABLED` env var (default true)
- `OCR_TESSERACT_LANGUAGE` env var (default `spa`)
- `OCR_TESSERACT_MIN_CONFIDENCE` env var (default 60)
- `OCR_COST_SAVER_MODE` env var (default false; if true, Tesseract is the first strategy for images)

---

### US-08: System verifies the language of the extracted text

**As the** system,
**I want to** detect the language of the extracted text,
**So that** we reject contracts not in Spanish before spending more resources.

**Acceptance criteria:**

- After successful extraction, the system runs language detection with `langdetect` or `lingua-py` over the first 2000 characters of the text
- If the detected language is `es` (Spanish) with probability greater than 0.85, it continues to the next step (classification, out of F1 scope)
- If the language is not Spanish, the system marks the submission `rejected_language` and notifies the user with a specific message
- If confidence is below 0.85 but the top language is Spanish, it continues with a logged warning (it may be technical text with many legal terms and proper nouns)
- If confidence is below 0.85 and the top language is not Spanish, it is marked `rejected_language`

---

### US-09: System reports the processing status

**As a** user or API client,
**I want to** query the status of my submission's processing,
**So that** I know whether it is in progress, complete, or failed.

**Acceptance criteria:**

- Endpoint `GET /v1/contracts/{submission_id}/status` returns the current state
- The endpoint is public and does not require authentication
- It returns `processing_status`, relevant timestamps, `analysis_id` when available, and `error_reason` if there is an error
- It does not expose sensitive information: never the contract content, never the extracted text, never the `delivery_target_hash`
- Returns HTTP 404 if the `submission_id` does not exist (or has expired)
- Caches with `Cache-Control: no-cache` to avoid staleness

---

### US-10: System discards the original file after processing

**As the** system,
**I want to** discard the original file as soon as the text is extracted,
**So that** we honor the privacy promise of not storing the contract.

**Acceptance criteria:**

- The original file is kept in memory (Python variable or Redis blob with short TTL) during processing
- Under NO circumstances is the file written to persistent disk
- If Redis is used for handoff between workers, the TTL is at most 300 seconds and is explicitly deleted on success or failure
- After extraction, the file is deleted immediately
- The extracted text is also not persisted in `ContractSubmission` or any other table
- The extracted text is passed in memory to F2 (classification) via the internal work queue
- The auditable metric is `extracted_text_token_count` in `ContractSubmission`, not the text itself

---

## 4. Business Rules

**BR-01:** The original contract file is never persisted to disk. It is kept in process memory (Python objects or Redis with TTL ≤ 300s) and discarded immediately after text extraction, successful or failed.

**BR-02:** The extracted contract text is not persisted in any table. It is passed in memory between pipeline features. Only the token count is persisted in `ContractSubmission.extracted_text_token_count` for cost auditing.

**BR-03:** Deduplication by `submission_hash` is strict. If two uploads have the same SHA-256, the same prior `analysis_id` is returned (if not anonymized) without re-processing. The exception is when the current rubric version differs from the one used in the previous analysis, in which case it is re-processed.

**BR-04:** The system prefers `PYPDF` over `VISION_LLM` over `TESSERACT` for cost. It only escalates to the next strategy when the previous one fails per the defined thresholds.

**BR-05:** LLM-provider calls use idempotency keys with format `submission_id:page_number:strategy:attempt_number` to avoid duplicate cost on HTTP client retries.

**BR-06:** Each `OcrJob` records the estimated LLM-call cost in USD cents (`cost_estimate_cents`) based on the current pricing table of the configured model. This metric is for internal reporting only; it is not exposed to the user.

**BR-07:** If a submission takes more than 5 minutes to complete, it is considered a timeout and marked `failed_extraction` with reason `TIMEOUT_EXCEEDED`. The user is notified.

**BR-08:** If the extracted text has fewer than 500 characters after normalization, it is considered an extraction failure (likely bad OCR) and the next strategy is attempted. If all strategies produce insufficient text, it is marked `failed_extraction` with reason `TEXT_TOO_SHORT`.

**BR-09:** The extracted text language must be Spanish with confidence over 0.85 to continue in the pipeline. Any other case results in `rejected_language`.

**BR-10:** The number of files per submission is capped at 50. This bound prevents abuse and keeps per-analysis cost bounded.

**BR-11:** The total number of processable pages per submission is capped at 80 (summing PDF pages and counting each image as one page). Exceeding it results in `TOO_MANY_PAGES`.

**BR-12:** Multi-file web submissions are treated as a single contract only within the explicit submit action. There is no conversational accumulation in MVP.

**BR-13:** The disclaimer "Esto no es asesoría legal" must have been explicitly accepted before any processing via the `disclaimer_accepted=true` form flag.

**BR-14:** `ContractSubmission` and `OcrJob` rows are physically deleted from the database when `expires_at < NOW()`. A cron job runs every 15 minutes to perform the cleanup.

## 5. Data Models

### 5.1 ContractSubmission

```sql
CREATE TABLE contract_submission (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    -- Identification and idempotency
    submission_hash TEXT NOT NULL,
    public_short_id TEXT NOT NULL UNIQUE,

    -- File information
    file_count INTEGER NOT NULL CHECK (file_count >= 1 AND file_count <= 50),
    total_size_bytes BIGINT NOT NULL,
    total_pages INTEGER,
    file_formats TEXT[] NOT NULL, -- e.g. ['pdf'] or ['jpg', 'jpg', 'png']

    -- Origin
    source TEXT NOT NULL CHECK (source IN ('web')),
    source_metadata JSONB DEFAULT '{}'::jsonb, -- IP or phone hash, user agent, etc., all hashed

    -- State and processing
    processing_status TEXT NOT NULL CHECK (processing_status IN (
        'received',
        'extracting',
        'extracted',
        'classifying',
        'analyzing',
        'completed',
        'failed_extraction',
        'failed_classification',
        'failed_analysis',
        'rejected_language',
        'rejected_type',
        'rejected_size',
        'expired'
    )),
    extraction_strategy_attempted TEXT CHECK (extraction_strategy_attempted IN ('pypdf', 'vision_llm', 'tesseract')),
    extraction_strategy_successful TEXT CHECK (extraction_strategy_successful IN ('pypdf', 'vision_llm', 'tesseract')),
    extracted_text_token_count INTEGER,
    extracted_text_language TEXT,
    extracted_text_language_confidence NUMERIC(3,2),

    -- Errors
    error_code TEXT,
    error_reason TEXT,

    -- Result association
    analysis_id UUID, -- optional FK to contract_analysis when completed

    -- Disclaimer
    disclaimer_accepted_at TIMESTAMPTZ NOT NULL,
    disclaimer_accepted_via TEXT NOT NULL CHECK (disclaimer_accepted_via IN ('web_checkbox')),

    -- Timestamps
    received_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    processing_started_at TIMESTAMPTZ,
    processing_completed_at TIMESTAMPTZ,
    expires_at TIMESTAMPTZ NOT NULL DEFAULT (NOW() + INTERVAL '24 hours'),

    CONSTRAINT analysis_required_when_completed CHECK (
        (processing_status = 'completed' AND analysis_id IS NOT NULL)
        OR (processing_status != 'completed')
    )
);

CREATE INDEX idx_submission_hash ON contract_submission(submission_hash);
CREATE INDEX idx_submission_status ON contract_submission(processing_status);
CREATE INDEX idx_submission_expires ON contract_submission(expires_at) WHERE expires_at IS NOT NULL;
CREATE INDEX idx_submission_analysis ON contract_submission(analysis_id) WHERE analysis_id IS NOT NULL;
CREATE INDEX idx_submission_public_short_id ON contract_submission(public_short_id);
```

### 5.2 OcrJob

```sql
CREATE TABLE ocr_job (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    submission_id UUID NOT NULL REFERENCES contract_submission(id) ON DELETE CASCADE,

    -- Job configuration
    strategy TEXT NOT NULL CHECK (strategy IN ('pypdf', 'vision_llm', 'tesseract')),
    attempt_number INTEGER NOT NULL DEFAULT 1 CHECK (attempt_number >= 1),
    model_used TEXT, -- e.g. 'anthropic/claude-sonnet-4', null for pypdf and tesseract

    -- Execution
    started_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    completed_at TIMESTAMPTZ,
    status TEXT NOT NULL CHECK (status IN ('running', 'success', 'failed', 'timeout', 'cancelled')),

    -- Results
    pages_processed INTEGER,
    pages_failed INTEGER,
    tokens_consumed INTEGER,
    cost_estimate_cents INTEGER,
    average_confidence NUMERIC(4,2), -- for Tesseract

    -- Errors
    error_code TEXT,
    error_message TEXT,

    -- Cleanup
    expires_at TIMESTAMPTZ NOT NULL DEFAULT (NOW() + INTERVAL '24 hours')
);

CREATE INDEX idx_ocr_job_submission ON ocr_job(submission_id);
CREATE INDEX idx_ocr_job_status ON ocr_job(status);
CREATE INDEX idx_ocr_job_expires ON ocr_job(expires_at);
```

### 5.3 Aggregate cost view (for internal observability)

```sql
CREATE VIEW v_ocr_daily_costs AS
SELECT
    DATE(started_at) AS day,
    strategy,
    model_used,
    COUNT(*) AS jobs_count,
    SUM(pages_processed) AS pages_total,
    SUM(tokens_consumed) AS tokens_total,
    SUM(cost_estimate_cents) AS cost_cents_total,
    AVG(EXTRACT(EPOCH FROM (completed_at - started_at))) AS avg_seconds
FROM ocr_job
WHERE status = 'success' AND started_at > NOW() - INTERVAL '30 days'
GROUP BY DATE(started_at), strategy, model_used
ORDER BY day DESC, cost_cents_total DESC;
```

### 5.4 Cleanup jobs (cron)

These jobs are not tables; they are scheduled jobs operating on the tables. Documented here so the implementer considers them.

```sql
-- Every 15 minutes: delete expired submissions
DELETE FROM contract_submission WHERE expires_at < NOW();

-- ON DELETE CASCADE on ocr_job removes associated OcrJobs

-- Every hour: mark abandoned submissions as expired (status received/extracting for over 1 hour)
UPDATE contract_submission
SET processing_status = 'expired',
    error_code = 'STUCK_IN_PROCESSING',
    error_reason = 'Submission stuck in processing'
WHERE processing_status IN ('received', 'extracting', 'classifying')
  AND processing_started_at < NOW() - INTERVAL '1 hour';
```

## 6. Integration Points

### 6.1 Input: HTTP API

The system exposes REST endpoints consumed by the web frontend.

- Next.js frontend calls `POST /v1/contracts/submit` with multipart
- After creating the submission, the frontend polls `GET /v1/contracts/{id}/status` every 3 seconds until `completed` or a terminal state

### 6.2 Input: Web image/PDF upload

The web app forwards PDFs and photos to the backend via multipart POST.

- Endpoint: same web upload endpoint as US-01
- Authentication: none for public MVP; rate limits and file validation apply
- Payload includes one or more `files[]` parts and delivery selection metadata
- The system holds files in memory during processing and never persists raw uploads

### 6.3 Output to F2 (Classification)

When the text is correctly extracted, F1 delivers it to F2 via an internal queue.

- Proposed technology: Redis Streams or RQ (Redis Queue)
- Message:

```json
{
    "submission_id": "uuid",
    "extracted_text": "string (in memory, not persisted)",
    "extraction_metadata": {
        "strategy_used": "vision_llm",
        "pages_processed": 12,
        "tokens_consumed": 8420,
        "language_detected": "es",
        "language_confidence": 0.94
    }
}
```

- The queue is processed by workers separate from the HTTP workers
- If the queue is saturated, F1 marks the submission as `extracted` and waits; the frontend keeps polling without error

### 6.4 External dependencies

## 8. LLM Prompts

### 8.1 Vision extraction prompt

**System:**

```
You are an OCR specialized in Salvadoran real estate contracts. Your only task is to faithfully transcribe the text in the image you are given.

Strict rules:
1. Transcribe ALL visible text in the image, without omitting clauses, numbers, dates, or legible signatures.
2. Preserve the document structure: titles, clause numbers, bullets, paragraphs.
3. If a word is illegible, transcribe it as [ilegible]. Do not invent content.
4. If a section is cut off by the image edge, indicate [texto cortado].
5. Do not add comments, observations, or analysis. Just transcribe.
6. Do not correct typos in the original document.
7. For tables, try to preserve structure with spaces or tabs.
8. For signatures, indicate [firma] without attempting to read them.
9. For seals or letterheads, transcribe what is legible and mark [sello: legible content].

Return only the transcribed text, no metadata.
```

**User (with attached image):**

```
This is page {page_number} of {total_pages} of a real estate contract. Transcribe all visible text.
```

### 8.2 Fallback prompt (when the model gets confused)

If the model response includes meta-textual comments like "Here is the text:" or "I have transcribed the following:", the system strips them with regex post-processing. If more than 5% of the output is meta-comment, the call is retried with a reinforced prompt:

```
ATTENTION: Your previous response included comments or explanations. DO NOT DO THAT.
Return ONLY the transcribed text from the image. Nothing before, nothing after.
```

## 9. Non-Functional Requirements

- **Extraction P50 latency:** under 30 seconds for PDF with extractable text; under 60 seconds for a single image; under 90 seconds for a 10-page scanned PDF via vision LLM.
- **Extraction P95 latency:** under 90 seconds for PDF with extractable text; under 180 seconds for scans.
- **Availability:** over 99% during business hours in El Salvador (UTC-6, 6:00 to 22:00).
- **Throughput:** support 100 concurrent submissions in the base config; graceful degradation up to 200 with queue and wait messages.
- **Target cost per analysis:** under $0.10 USD in LLM for a 15-page scanned contract.
- **Zero files on persistent disk:** structural property verifiable by an audit script that mounts the volumes and checks no user files exist.
- **Idempotency:** the same submission hash returns the same analysis without re-processing.
- **Observability:** Prometheus metrics exposed for per-strategy latency, per-strategy success rate, daily aggregate cost, language rejection rate.
- **Logging:** structured JSON; never includes contract text; hashes and IDs are logged for correlation.
- **OpenRouter failure resilience:** circuit breaker opens after 5 consecutive failures in 60 seconds, recovers after 5 minutes. When open, new submissions use Tesseract directly.

## 10. Open Questions

1. What is the default vision model on OpenRouter? Reasonable options are Claude Sonnet 4 (high quality, medium cost), GPT-4o (high quality, medium cost), or Gemini Flash (cheaper, variable quality). The decision affects per-analysis cost and OCR quality on poorly lit photos.

2. Is a manual retry endpoint (`POST /v1/contracts/{id}/retry-ocr`) needed accessible to the user, or is retry only automatic internally? A public endpoint opens an abuse surface (re-running extraction costs). Internal-only retry leaves no recourse for a user who had bad luck with OCR.

3. What is the rate-limit policy per IP / delivery target? Initial proposal: 5 submissions per hour per IP, 3 per phone/email hash.

4. How are HEIC files handled in production? The `pyheif` library requires `libheif` installed at the system level, and `pillow-heif` is a more modern alternative. The decision affects the Dockerfile and the reliability of iOS HEIC support.

5. Is the `application/pdf` format allowed when it actually contains JavaScript or interactive forms? These can include malicious content. Proposal: reject PDFs with JavaScript, alert, and ask for a new version without JS.

6. What if the user sends the same contract twice with a minor change (one paragraph modified)? The hash will differ, so it will be processed as a new analysis. Is that OK or do we want to detect "variants" of the same contract? Detecting variants requires textual similarity, which is expensive and prone to false positives.

7. Does the internal queue between F1 and F2 (Redis Streams or RQ) require at-least-once or exactly-once delivery? To preserve LLM-call idempotency, exactly-once is desirable but more complex. At-least-once with `submission_id`-based deduplication may be sufficient.

8. In `cost_saver_mode`, is Tesseract the first strategy for images? This reduces cost but degrades quality when photos are in real conditions (bad lighting). The comparative success rate should be measured before enabling it by default.

# Design Patterns — F3: Legal Corpus & Citation Retrieval

> Generated: 2026-05-15
> Cross-cutting patterns: `../_shared/GLOBAL_ASSUMPTIONS.md` §12.

---

## Patterns Applied

### Versioned Immutable Catalog

**Why this pattern fits:** Reproducing an old report months later must produce the same citations even if the law has been reformed. Mutable corpora lose this property. Treating each corpus as an immutable named snapshot with an `is_active` pointer to the current one matches the requirement and Casa Segura's privacy / audit posture.

**What it covers:**
- `CorpusVersion` table with partial unique index on `(is_active) WHERE is_active = TRUE`
- All dependent rows (`LegalDocument`, `LegalChunk`) keyed by `corpus_version`
- `ContractAnalysis.corpus_version` pinned at analysis time
- Retrieval is **always** filtered by version (no implicit "current" lookup at F4 level)

**What it does NOT cover:**
- Reactive deprecation of chunks within a published version (PRD §10 OQ-6, out of MVP)

**Implementation:** `corpus/infrastructure/django/models.py`, the partial unique index, retrieval functions always take `corpus_version` explicitly.

---

### Strict Threshold (Cite-or-stay-silent)

**Why this pattern fits:** The product's defensibility hinges on not inventing law. The simplest enforceable rule is a hard similarity threshold: below 0.65, return empty. F4 then is forced to label the finding `market_based` or `unverifiable_legal`.

**What it covers:**
- `LegalCitationService.retrieve_legal_basis` filters by threshold before returning
- The F4 prompt explicitly forbids generating citations not provided by F3
- Logs always record `results_count_above_threshold` and `top_score` for auditability

**What it does NOT cover:**
- Per-criterion threshold tuning (configurable, but the default is fixed at 0.65)

**Implementation:** `LegalCitationService.retrieve_legal_basis` body; configuration `RAG_DEFAULT_THRESHOLD=0.65`.

### Hybrid Search (regex + semantic)

**Why this pattern fits:** Many findings text generated by F4 already contains the article reference (because the criterion was prompted with `Criterion.legal_anchor`). Doing semantic search in those cases wastes compute and risks returning a near-but-not-exact chunk. A short regex pass catches the common cases (`Art. N CC`, `Art. N LPC`, etc.) and short-circuits to a direct lookup.

**What it covers:**
- `HybridMatcher.find_exact_anchor(text, version)` runs the regex list from PRD §6.2
- On hit, `LegalChunkRepository.get_by_anchor` returns the exact chunk
- `similarity_score=1.0` is recorded so F4/F6 know it's an authoritative match

**What it does NOT cover:**
- Multi-article references in one finding text (only the first hit is taken; future enhancement could collect all)

**Implementation:** `corpus/application/services/hybrid_matcher.py`, regex constants in `corpus/infrastructure/parsing/article_regex.py`.

---

### Adapter (EmbeddingModel)

**Why this pattern fits:** sentence-transformers can be swapped (e.g., upgrade to a larger model). Pinning all call sites to the concrete library would make the swap painful. The adapter exposes a minimal interface (`encode`, `encode_batch`, `dim`) and hides the dependency.

**What it covers:**
- `corpus/infrastructure/embeddings/sentence_transformer_adapter.py` implements the `EmbeddingModel` protocol
- Tests can substitute a `FakeEmbeddingModel` that returns deterministic vectors
- Configuration `EMBEDDING_MODEL_NAME` controls the underlying model id

**What it does NOT cover:**
- Re-ingesting the corpus when the model changes — that's an operations task documented in `BR-F3-09`

**Implementation:** Adapter class plus a Django settings option to override at startup.

---

### Repository (DjangoFullRepository specialization)

**Why this pattern fits:** Vector queries are not Django-ORM-idiomatic. We isolate them in repository methods (`cosine_search`, `get_by_anchor`) so the rest of the codebase doesn't import `pgvector.django` operators directly.

**What it covers:**
- `LegalChunkRepository.cosine_search(version, q, top_k, threshold, filter_tags, prefer_anchors)`
- `LegalChunkRepository.get_by_anchor(law_id, anchor, version)`

**Implementation:** Uses `pgvector.django.CosineDistance` operator inside the repository; service layer is vector-blind.

---

### Anti-corruption layer (Markdown → Domain)

**Why this pattern fits:** Markdown ingestion is structurally complex (frontmatter, `### Art. N` headings, optional verbatim blocks, tags). The parser normalizes this into well-typed Pydantic structures so the rest of F3 deals with `ParsedDocument` / `ParsedArticle` only.

**What it covers:**
- `MarkdownCorpusParser.parse_file(path) -> ParsedDocument`
- Frontmatter validation (required fields, status enum, ISO dates)
- Body split on `### Art. N` headings (regex)
- Tag normalization (lowercase, no accents, no special chars)
- Detection of verbatim blocks (fenced code with `language: verbatim` or labelled paragraph)

**Implementation:** `corpus/infrastructure/parsing/markdown_parser.py`.

---

### Singleton-by-process (EmbeddingModel)

**Why this pattern fits:** Loading the 80 MB sentence-transformers model takes ~3 s; repeating it per request would dominate latency. Each process loads once at warm-up.

**What it covers:**
- Module-level lazy instantiation in `embedding_adapter.py`
- Health-check endpoint warms the model
- Celery `worker_process_init` signal also triggers warm-up

**Implementation:** `_model = None` + `get_model()` accessor.

## Patterns Considered and Rejected

### LLM re-ranker

PRD §8.1 suggests this; the PRD itself says "not in MVP". Re-ranking improves precision marginally at material LLM cost and complexity. Reject for MVP; revisit when ground-truth precision drops below product target.

### Cache retrieve results by query hash

Tempting: cache `LegalCitationService.retrieve_legal_basis` outputs in Redis keyed by `(query_text_hash, corpus_version)`. Reject because: queries are sub-150 ms; caching adds invalidation complexity (corpus changes require cache flush); cache hit rate would be modest (findings are per-contract).

### Hierarchical chunks (sub-article splitting)

Tempting: split `Art. 19 LPC` into 19.a, 19.b, ..., 19.p sub-chunks. Reject for MVP because: the markdown source already supports `### Art. N lit. M`, which the parser handles via `anchor=art-19-j`. Only when an article is very long and the paraphrase becomes unmanageable do we split; that's an editorial decision, not a system one.

### Multiple-vector retrieval (ColBERT, multi-vector)

Higher precision; much higher storage. Reject for MVP. Single-vector with curated paraphrases is sufficient.

### Pre-compute query embedding cache per finding text

Findings are generated freshly per analysis; no repeated text. Cache hit rate would be near zero.
